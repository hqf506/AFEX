# A2.2 Trusted Runtime Client Design

Status: DESIGN ONLY — DISABLED AND BLOCKED FROM IMPLEMENTATION

## Executive decision

AFEX requires three non-interchangeable client boundaries:

1. User-context Supabase client for Auth and RLS-controlled operations.
2. Administrative service-role client for explicitly approved server-only administration.
3. Future Core V2 trusted command client with a dedicated LOGIN and a non-generic EXECUTE-only interface.

No existing client satisfies boundary 3. No connection architecture is selected because LOGIN, membership, pool, reset, secret-delivery, network, and connection-limit evidence is missing. P2D.20 must remain uncalled.

## Boundary architecture

The future client is server-only and may be imported only by an approved server facade. It cannot export a driver, Supabase client, connection, transaction, `rpc`, `from`, query string, schema selector, or raw response. It accepts only a sealed Authorization Context request produced in the same request.

The database allowlist contains exactly:

`public.acquire_atomic_order_command_v1(uuid, uuid, uuid, text, text, text, text, timestamptz)`

`canonicalize_atomic_order_json_v1(jsonb)` remains owner-only and is never callable by the application client.

## Proposed narrow API

| Method | Inputs | Output | Retry/idempotency | Status |
|---|---|---|---|---|
| `acquireAtomicOrderCommand` | Sealed auth context; stable client key; canonical payload bytes/text per A1; derived projection; correlation reference; retention; abort signal | Frozen A1 acquisition union: `created`, `replay`, `in_progress`, `fingerprint_conflict` with validated identifiers only | One transport attempt by default. Retry/reconcile uses identical actor/scope/key/canonical bytes. | Future, blocked. |
| `issueAtomicOrder` | Reserved future execution request that includes a valid acquisition result | Stable A1 execution/error union | Never retries financial execution blindly; no legacy fallback | Deferred to Executor phase; not part of P2D.20 acquisition. |
| `replayAtomicOrderCommand` | Same sealed identity and idempotency tuple or approved command reference | Stable replay/status result without mutable business reconstruction | Read/reconcile only; never invents new key | Deferred until a reviewed database status/replay entrypoint exists. |

No arbitrary method name, SQL, table, schema, or connection is an input.

## Input validation and authority

- UUIDs must satisfy frozen canonical forms.
- Canonical payload and projection must satisfy A1/P2D.18A exactly.
- Idempotency key is opaque, length-limited, stable, and redacted/hash-only in logs.
- Actor, tenant, branch, employee, role, capability, projection, and retention are server-derived.
- Database independently validates trusted evidence; application validation is not a replacement.

## Error union

Stable application categories:

- `AUTHENTICATION_REQUIRED`
- `ACTOR_NOT_AUTHORIZED`
- `TENANT_MISMATCH`
- `BRANCH_MISMATCH`
- `INVALID_COMMAND`
- `IDEMPOTENCY_CONFLICT`
- `COMMAND_ALREADY_COMPLETED`
- `COMMAND_IN_PROGRESS`
- `TRANSIENT_DATABASE_FAILURE`
- `TIMEOUT_UNKNOWN_OUTCOME`
- `REPLAY_REQUIRED`
- `RUNTIME_CONFIGURATION_UNAVAILABLE`
- `TRUSTED_CLIENT_DISABLED`
- `INTERNAL_INVARIANT_VIOLATION`

SQLSTATE and driver details are internal mappings. Unknown dispositions, malformed rows, identity mismatch, cleanup failure, and unclassified errors map to invariant failure and stop.

## Timeout and cancellation

Timeout values must be frozen by the A1 performance contract and connection ADR; this phase does not invent a numeric value. Cancellation does not imply rollback unless the database/driver confirms it. A timeout after send is an unknown outcome resolved only with the same idempotency tuple. Aborted Vercel requests and process shutdown must not return a possibly contaminated connection.

## Disabled-by-default gate

Future implementation is guarded by `AFEX_CORE_V2_ATOMIC_ORDER_ENABLED=false`, but this phase does not add the variable. Startup validation when enabled must require the approved connection type, secret, LOGIN identity, membership attestation version, pool sanitation proof, exact function contract/hash, and environment. Missing or unsafe configuration fails startup or the trusted call closed in every environment. Development cannot silently weaken Production validation.

When disabled, legacy behavior remains unchanged. When later enabled for a request, there is no dual write, shadow mutation, or fallback to legacy after Core V2 accepts/possibly accepts a command. Optional shadow work may only be read-only and separately approved.

## Exactly-once boundary

The logical attempt owns one stable key. Duplicate taps, browser retries, offline replay, server retry, and mobile network retry reuse it. A different payload with the same key yields conflict. An uncertain outcome never generates a replacement key. Receipt, PDF, WhatsApp, email, and other effects consume committed outbox/status evidence in future phases; they are not retried as part of acquisition and must deduplicate independently.

## Observability

Allowed: correlation ID, request ID, command ID after validation, stable error category, safe tenant/branch/actor pseudonyms, duration by stage, retry count, selected client/pool architecture identifier, role-activation attestation result, and SQLSTATE category.

Forbidden: connection URLs, passwords, keys, JWTs, cookies, PINs, raw idempotency keys, canonical payload, fingerprint projection, customer data, payment evidence, raw SQL, or unrestricted database diagnostics.

## Security invariants

- Server-only import graph and no client-component reachability.
- Dedicated secret never shares the service-role variable.
- One request cannot reuse another request’s sealed context.
- Only exact acquisition is executable.
- No direct relation/sequence access.
- No role/session claims without runtime proof.
- Connection is destroyed/quarantined on uncertain cleanup.
- No generic privileged API escapes the module.
