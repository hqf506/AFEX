# A2.3 Architecture Decision Record

Status: CONDITIONALLY DECIDED; implementation blocked by external gates

## Decision

Prefer a dedicated NOINHERIT application LOGIN connecting from a server-only Next.js Node trusted facade through the Supabase transaction pooler, activating the existing NOLOGIN `afex_core_runtime` only inside one explicit pinned transaction, and calling only the exact P2D.20 signature.

The decision becomes effective only if external and isolated evidence proves transaction pinning, role activation, automatic transaction-state removal, cancellation behavior, capacity, TLS, Vercel support and cleanup. Until then, the live legacy route is unchanged and P2D.20 is not called.

## Ranking

| Rank | Architecture | Status | Principal failure modes | Operational/security impact |
|---:|---|---|---|---|
| 1 | Dedicated LOGIN + Supabase transaction pooler | Preferred pending evidence | Statement multiplexing, unsupported role semantics, uncertain cancellation/reset | Best expected Vercel capacity and least standing privilege if proven. |
| 2 | Separate trusted command service + bounded pool | Acceptable fallback | Added hop/SPOF, signing/replay errors, independent deployment failure | Strong secret/pool isolation; highest operational cost. |
| 3 | Vercel direct PostgreSQL + bounded driver pool | Deferred | Connection storms, network/IPv4, region latency, freeze/thaw pool reuse | Strong connection control but capacity uncertainty. |
| 4 | Session pooler | Rejected pending exceptional proof | Role/GUC/prepared/temp/advisory contamination | Cleanup burden too high for current evidence. |
| 5 | PostgREST service_role, direct Runtime login, browser switching, generic wrapper | Rejected | RLS bypass, identity-contract violation, generic privilege exposure | Fails approved security model. |

## Decision gates

All must pass: security contract, role isolation, pool transaction semantics, cleanup, capacity, Vercel compatibility, Supabase supportability, secret lifecycle, observability, rollback/revocation, latency and operational ownership.

## Consequences

- `afex_core_runtime` remains NOLOGIN and owns nothing.
- A new narrowly scoped credential and driver may eventually be required.
- Next.js trusted route must explicitly pin Node and remain server-only.
- Physical connection lifecycle becomes security-critical code.
- Unknown commit response preserves idempotency and triggers same-key reconciliation.
- No generic query surface, service-role reuse, dual write or legacy fallback is permitted.

## Reversal criteria

If transaction pooler proof fails, move to the separate command-service evaluation rather than weakening identity or cleanup. If no architecture meets capacity/security gates, Core V2 remains disabled. Convenience is not a reversal criterion.
