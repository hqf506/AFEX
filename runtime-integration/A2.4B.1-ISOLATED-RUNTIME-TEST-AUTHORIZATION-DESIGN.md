# A2.4B.1 Isolated Runtime Test Authorization Design

Status: DESIGN APPROVED; EXECUTION NOT AUTHORIZED

## Authorization boundary

This design permits preparation for a future disposable test only. It does not authorize SQL generation or execution, database contact, package installation, credential creation, a transport implementation, or application integration.

## Disposable environment

The future environment must be separate from business execution and contain only:

- One dedicated short-lived test `LOGIN` with no object ownership and no inherited runtime authority.
- One dedicated `NOLOGIN` test role with only the harmless test capability.
- One SET-only membership edge from the test LOGIN to the test role: `SET=true`, `INHERIT=false`, `ADMIN=false`.
- One harmless constant-return or catalog-only function owned and secured for the test role.
- No access to business tables, P2D.20, Core V2 ledgers, customer data, orders, payments, inventory, application routes, or notification systems.
- A short-lived credential delivered outside source control and evidence, followed by explicit revocation and cleanup.

The setup must be independently reviewed and attested before any harness connection. Cleanup failure fails the entire test campaign.

## Test objectives

| ID | Objective | Bounded action | Required observation |
|---|---|---|---|
| B01 | Explicit-transaction backend pinning | Use one checked-out client from transaction start through commit and separately through rollback | One backend PID for every statement in each explicit transaction |
| B02 | Local role activation | Activate only the fixed test role with transaction-local scope | `session_user` remains the test LOGIN; `current_user` changes only inside the transaction |
| B03 | Commit cleanup | Commit after activation, reacquire connections, and inspect identity | Test role is absent after commit and on every later checkout |
| B04 | Rollback cleanup | Force a reviewed harmless failure, roll back, reacquire, and inspect | No role, transaction, GUC, search-path, or lock residue |
| B05 | Statement cancellation cleanup | Cancel a bounded harmless statement inside an activated transaction | Connection is rolled back and sanitized or destroyed before reuse |
| B06 | Client timeout cleanup | Trigger a client-side bounded timeout | Outcome is classified; uncertain connection is quarantined and destroyed |
| B07 | Abrupt disconnect cleanup | Terminate the disposable client during an activated transaction | Server transaction ends; no privileged state appears on subsequent reuse |
| B08 | Sequential contamination | Alternate synthetic clients/scopes over repeated checkouts | Zero cross-request identity, GUC, path, lock, or marker contamination |
| B09 | Concurrent contamination | Run bounded concurrent synthetic clients with distinct markers | Every observation remains associated with the correct logical client |
| B10 | Transaction advisory lock | Contend on one derived synthetic lock key and test both completion paths | Correct exclusion and automatic release at commit and rollback |
| B11 | Prepared-statement prohibition | Inspect configuration and exercise only unnamed/nonpersistent statements | No persistent preparation is requested or retained |
| B12 | Quarantine on uncertainty | Inject launch, transaction, cancel, timeout, and disconnect uncertainty | The affected connection never returns to the reusable pool |

## Identity observation sequence

Every applicable case records safe observations at these boundaries:

1. Immediately after checkout and before transaction start.
2. After transaction start and before activation.
3. During transaction-local activation.
4. Immediately before commit or rollback.
5. Immediately after transaction completion on the same client where valid.
6. After release and reacquisition, including a later checkout that may receive the same backend PID.

Only approved test role names, booleans, timestamps, backend PIDs, safe transaction identifiers, and pseudonymous case IDs may be recorded.

## Quarantine contract

A connection is uncertain after cancellation, client timeout, abrupt disconnect, protocol error, ambiguous transaction completion, failed rollback, identity mismatch, or cleanup mismatch. An uncertain connection must be destroyed, not released for reuse. Automatic retry with weaker settings is prohibited. The pool must be drained after contamination, unexplained identity, or cleanup failure.

## Cleanup and revocation

The future operator sequence must stop the harness, drain the pool, verify no test sessions or locks remain, revoke the credential and membership, remove the harmless test objects and roles through separately reviewed cleanup SQL, and run a read-only absence attestation. Evidence must prove cleanup without exposing secrets.
