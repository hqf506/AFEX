# A2.3 Capacity and Connection Limit Plan

Status: formulas frozen; numeric approval awaits Production metadata

## Variables

| Symbol | Meaning |
|---|---|
| `Imax` | Maximum simultaneous warm Vercel instances for the trusted route |
| `P` | Maximum physical database connections per instance |
| `Cpool` | Pooler client concurrency limit for the dedicated LOGIN |
| `Cdb` | Supabase database connection limit available to the project |
| `Radmin` | Connections reserved for Supabase management, migrations, monitoring and break-glass |
| `Rother` | Worst-case connections used by all non-Core application/services |
| `S` | Safety reserve for failover and measurement uncertainty |
| `L95` | P95 acquisition transaction duration in seconds |
| `λ` | Sustained logical command arrival rate per second |
| `B` | Worst-case retry/duplicate amplification factor |
| `T` | Timeout occupancy duration in seconds |

No numeric value is present in repository evidence and none is invented.

## Conservative bounds

Direct/session pool bound:

`Imax × P ≤ Cdb − Radmin − Rother − S`

Transaction-pool backend demand must satisfy both provider queue limits and:

`ceil(λ × B × L95) ≤ Cdb − Radmin − Rother − S`

If timed-out work may retain backend occupancy, stress demand includes:

`ceil(λ × B × max(L95, T))`

Dedicated LOGIN connection limit must be no greater than the approved Core V2 allocation and no greater than provider/pool capacity. It is finite. Per-instance pool size should start at the minimum proven viable—potentially one—but no number is approved before load evidence.

## Load components

- Normal POS checkout throughput.
- Duplicate taps despite UI locks.
- Offline/Capacitor reconnect bursts.
- Browser/server retries using the same key.
- Timeout-after-commit reconciliation.
- Cold-start instances creating pools concurrently.
- Preview/development deployments, which must use separate credentials/capacity or remain disabled.
- Pool failover/reconnect bursts.

## Controls

Bounded queue, acquisition timeout, per-instance cap, global/provider cap, circuit breaker, backpressure before database checkout, same-key retry suppression, jitter for safe read/reconciliation, connection lifetime/rotation, and shutdown drain. Pool objects may be process-global only after their per-instance limits and cleanup behavior are proven.

## Required Production evidence

- Compute tier and database `max_connections`/provider allocation metadata.
- Supavisor client/backend limits and dedicated user limit.
- Current peak non-Core connection use and reserved management need.
- Vercel maximum/observed concurrent instances and region.
- Measured cold/warm `L50/L95/L99`, transaction time, queue time and timeout occupancy.
- Peak POS command and retry rates, including mobile reconnect events.
- Failover and credential-rotation connection overlap.

Capacity fails closed if any variable remains unbounded at enablement review.
