# A2.4B.2 Final LOGIN Privilege Contract

Status: NORMATIVE DESIGN; NOT INSTALLED

## Identity attributes

The future dedicated application identity must satisfy all of the following:

| Property | Required state |
|---|---|
| LOGIN | True |
| INHERIT | False |
| SUPERUSER | False |
| BYPASSRLS | False |
| CREATEDB | False |
| CREATEROLE | False |
| REPLICATION | False |
| CONNECTION LIMIT | Positive finite reviewed value |
| VALID UNTIL | Finite reviewed expiry, or an explicitly approved rotation policy with equivalent enforcement |
| Ownership | No database, schema, relation, sequence, function, policy, extension, publication, or other object |
| Membership | None in either direction; no SET ROLE capability is required |
| Role configuration | Exact reviewed safe baseline only; no request-controlled authority or resolution setting |

## Allowed capability

The only direct application database capability is EXECUTE on the exact signature:

`public.acquire_atomic_order_command_v1(uuid, uuid, uuid, text, text, text, text, timestamp with time zone)`

The grant is signature-specific. No overload, helper, future function, schema wildcard, or default privilege is implied.

## Explicit denials

The LOGIN must have:

- No direct table, view, materialized-view, foreign-table, or column privilege.
- No direct sequence privilege.
- No schema CREATE privilege or schema ownership.
- No generic function EXECUTE and no EXECUTE on the canonicalizer or unrelated functions.
- No role membership, role administration, inherited privilege, browser role, managed role, owner role, service role, worker role, or issuer role path.
- No ability to alter objects, policies, ownership, RLS, grants, roles, or default privileges.
- No direct access to P2D.19/P2D.20 storage objects.

Effective privilege attestation must account for PUBLIC, default ACLs, ownership, membership, schema reachability, and exact function ACLs. A direct-ACL inventory alone is insufficient.

## Secret and operational lifecycle

- Credential use is server-only and isolated from every existing Supabase/service-role variable.
- Values never appear in source, process arguments, logs, evidence, diagnostics, or client bundles.
- Rotation uses a reviewed bounded overlap, proves the new credential, then revokes the old one without fallback.
- Emergency response can disable LOGIN immediately, terminate/quarantine its sessions, and revoke the exact EXECUTE privilege.
- Revocation must be followed by proof that connection, function execution, table access, sequence access, other-function execution, and membership all fail as expected.

## Activation prerequisite

No runtime activation occurs until exact role attributes, zero ownership, zero membership, exact direct/effective ACL inventory, function safety, credential lifecycle, runtime denials, and revocation behavior pass independent attestation and isolated tests.
