# A2.3G Next Phase Decision

## Primary next phase

`A2.3H — Provider Confirmation and Runtime Test Design`

## Reason

The main architecture blockers are not source-code gaps. G1–G4 require scoped Supabase confirmation, and G5/G10/G11 require carefully designed isolated runtime proof. G6–G9 and G12 also need provider, capacity, lifecycle, and observability evidence. Beginning a connection implementation or installing a driver would encode assumptions that the gates explicitly prohibit.

## A2.3H scope

- Finalize non-secret Supabase and Vercel support requests.
- Normalize accepted provider responses and identify conflicts.
- Specify the isolated environment, synthetic identities, credential handling, test matrix, evidence artifacts, stop rules, and teardown.
- Define exact success/failure criteria for transaction pinning, role activation, cleanup, cancellation, unknown outcomes, advisory locks, prepared statements, capacity, and contamination.
- Produce no executable SQL, provider connection, package change, runtime implementation, or activation unless separately authorized.

## Parallel design eligibility

The following may be proposed as separate, independently approved phases but do not replace A2.3H:

- Dedicated LOGIN/membership SQL design: `LOGIN_SQL_DESIGN_MAY_BEGIN`.
- Driver comparison ADR: `DRIVER_INSTALLATION_BLOCKED_BUT_ADR_ALLOWED`.
- Credential-free disabled adapter declarations: `PURE_SKELETON_IMPLEMENTATION_MAY_BEGIN`.

## Frozen sequencing

- Codex may later produce complete SQL for manual review, but no SQL execution occurs without explicit approval.
- No password or secret is stored in Git.
- No `service_role` fallback, dual write, P2D.20 application call, route activation, or fallback to legacy after an uncertain send.
- Package installation requires separate approval after the ADR.
- Implementation begins only from a clean reviewed working tree.

The transaction-pool architecture is neither approved nor failed at this stage; it remains blocked pending evidence.
