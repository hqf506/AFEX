The additive amendment is internally deterministic and is ready for independent PD.4B review. It selects `COMBINED_SERVER_TIMEOUT_AND_DESTROY`, requires no private pg API, and preserves all frozen inputs. PD.5 may begin only after this amendment is independently reviewed and merged.

## Public/private boundary

Public authority includes Pool/Client construction, checkout/query/release, `release(true)`, pool/client events, pool aggregate counts, documented timeout configuration, and documented `getTransactionStatus()`. The latter is implemented in the pinned runtime but missing from the pinned type declarations; PD.5 needs a narrow reviewed type adaptation.

Private and prohibited authority includes `Client.cancel`, `processID`, `secretKey`, `_txStatus`, query queues/active-query state, socket/parser internals, and pool internal arrays. AbortSignal is not an inspected QueryConfig capability. No implementation may synthesize a CancelRequest from private backend keys.

## Contradiction findings

One material abstraction mismatch was found, but it is resolved by the amendment: the Fake Driver's deterministic CANCEL event is not a supported high-level pg cancellation operation. The old rule “cancel once, await settlement” now means server-side timeout cancellation followed by ordinary protocol settlement; if the adapter deadline wins, the connection is destroyed.

The Fake Driver's PID is symbolic and cannot become physical-backend authority. FIFO ordering and aggregate pool counts do have public real-pool equivalents, while waiter identity does not. The documented runtime transaction-status method has a declarations gap, not a semantic contradiction. No frozen artifact requires mutation.

## Timeout ownership

Checkout and connection establishment precede borrower ownership and are stage-tagged despite sharing a pg configuration option. Within a transaction the strict order is lock timeout at or before statement timeout, then application deadline, then overall deadline. Settlement and rollback budgets begin only in their respective phases and must fit the overall budget. Driver `query_timeout` is prohibited as Production cancellation authority because it rejects locally without proving backend or protocol settlement.

## Cancellation decision

Decision: **`COMBINED_SERVER_TIMEOUT_AND_DESTROY`**. Transaction-local server timeouts provide deterministic database-side termination. A later adapter deadline supplies a safety escape. Ordinary server-timeout settlement permits one rollback; a winning local deadline or failed settlement mandates destructive release. Explicit cancellation attempts are zero.

This rejects every model requiring private pg fields, durable backend identity, or undocumented cancellation behavior and remains conservative under transaction pooling.

## Query settlement and transaction authority

Normal pg promise settlement plus a post-cycle `getTransactionStatus()` reading and absence of error/timeout uncertainty constitute bounded settlement evidence. A Promise alone, especially a `query_timeout` rejection, is insufficient. Adapter state and wire-derived status are combined; `I`, `T`, and `E` map to idle, in-transaction, and failed-transaction. Missing, contradictory, or unavailable status is unknown and destroys.

## Rollback and release/destroy decision

Ordinarily settled in-transaction failures, statement timeouts, and lock timeouts receive at most one rollback. Socket/protocol/client uncertainty, local-deadline victory, settlement failure, rollback failure, unknown state, and ambiguous COMMIT outcome skip or fail rollback and destroy.

Normal release uses `client.release()` exactly once only after every settlement, transaction-terminal, sanitation, identity, and health guard passes. Destruction uses documented `client.release(true)` exactly once and is mandatory whenever reuse safety is not proved.

## Failure vocabulary and sanitization

The rejected first review found that ordinary query failure had no deterministic final code. The correction adds `PG_QUERY_FAILED` for an ordinarily settled, non-timeout/non-connection query rejection and `PG_POOL_SHUTDOWN` for shutdown-before-ownership. These are the only new codes. The amendment now supplies a complete code table with owning stage, reuse/rollback consequence, SQLSTATE relation, and a universal no-automatic-business-retry rule.

Final-code precedence is independently reconciled as: ambiguous transaction outcome; connection/socket/protocol/client loss; unknown settlement/status; rollback failure/timeout; identity/sanitation/release safety; pool lifecycle; originating query/statement/lock failure. A more specific later safety failure becomes the one primary result code while an earlier closed code may remain only as a bounded stage event.

The SQLSTATE allowlist remains exactly `57014`, `55P03`, `40001`, `40P01`, `25P02`, `08000`, `08001`, `08003`, `08004`, `08006`, `08007`, and `08P01`. Classification uses code plus stage, never raw message text. Credentials, endpoints, identifiers, query text/values, arbitrary messages, and production stack traces are prohibited.

## Pool/client error decision

A non-throwing pool error listener is mandatory and records sanitized evidence for an idle client pg-pool removes. A checked-out client has ownership-scoped error/end observation; any such event selects destroy. An affected idle client does not automatically poison the whole pool. Shutdown races cannot yield normal success without all terminal guards.

## Compatibility review

The generic contract preserves direct PostgreSQL, PgBouncer transaction-pooling, and Supavisor transaction-mode compatibility by using one explicit transaction per borrower, transaction-local settings, unnamed statements, and no session/PID affinity. Provider execution remains unproved. Vercel requirements are limited to future global-pool reuse, deadline headroom, capacity, suspension, idle cleanup, and cold/hot tests; `pool.end()` per request is prohibited.

## Scenario coverage

The original review blockers were limited to RD-002's missing ordinary-query code, RD-006's two possible race outcomes, RD-023's two unspecified shutdown outcomes, and the absence of explicit closure columns. All are corrected without changing the accepted cancellation model.

The corrected table has exactly 23 unique IDs and explicit closed columns for trigger ordering, provider scope, settlement, transaction status, rollback, terminal classification, release action, failure code, retry, and evidence limitation. The terminal vocabulary is `COMPLETED_SAFE`, `ROLLED_BACK_SAFE`, `CHECKOUT_REJECTED`, `CONNECTION_REJECTED`, `DESTROYED_UNSAFE`, and `POOL_EVENT_ONLY`. Release actions are `NORMAL_RELEASE`, `DESTROY_RELEASE`, and `NO_RELEASE`.

RD-002 now freezes ordinary error settlement, `E`, one successful rollback to `I`, `ROLLED_BACK_SAFE`, `NORMAL_RELEASE`, and `PG_QUERY_FAILED`. RD-006 is only `RESULT_BEFORE_APPLICATION_DEADLINE` and ends `COMPLETED_SAFE`; RD-004 independently owns `APPLICATION_DEADLINE_BEFORE_SETTLEMENT` and ends `DESTROYED_UNSAFE` with `PG_QUERY_SETTLEMENT_UNKNOWN`. RD-023 is only `POOL_SHUTDOWN_BEFORE_BORROWER_OWNERSHIP`, producing `CHECKOUT_REJECTED`, `NO_RELEASE`, and `PG_POOL_SHUTDOWN`; checked-out uncertainty remains covered by RD-014/RD-016.

Provider scope uses only `GENERIC` and, for actual cancellation-provider proof in RD-005, `PROVIDER_REQUIRED`; the unused closed values remain available without making a proof claim. No row relies on PID/session affinity, private cancellation, or persistent session state. Independent audit result: IDs 23/23, duplicates 0, missing IDs 0, conditional outcomes 0, missing terminal/action/code fields 0, private-API scenarios 0.

Exactly-once invariants remain: ambiguous COMMIT is never replayed; unknown outcome never re-executes a command; ambiguous COMMIT never normally releases; rollback never proves a failed COMMIT did not commit; and timeout never automatically retries a business command. Every row records automatic business retry `NO`. The scenarios remain specifications only and were not executed.
