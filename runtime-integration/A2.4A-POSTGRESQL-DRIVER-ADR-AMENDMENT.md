# A2.4A PostgreSQL Driver ADR Amendment

## Amendment identity

- Amendment: `A2.5.PD.2_POOLDRIVER_CONTRACT_FREEZE`
- Status: `ADR_REMAINS_VALID_BUT_REQUIRES_AMENDMENT`
- Authoritative baseline: `16d363173f22cc9d384607598b5acf47c61aca52`
- Selected direction: `RETAIN_PG_TRANSACTION_POOL_DIRECTION`

## Original ADR relationship

This document supplements `runtime-integration/A2.4A-POSTGRESQL-DRIVER-ADR.md`. It does not replace or edit that record. The original selection of node-postgres remains valid, subject to every narrower boundary in this amendment.

## Node-only runtime boundary

Future raw-driver code is restricted to a private server-only module running in the Next.js Node.js runtime. Browser import, client-component import, public re-export, and execution from any browser-reachable bundle are prohibited. The present phase authorizes evidence-contract documents only.

## Edge prohibition

Next.js Edge runtime and Supabase Edge Functions are outside this decision. Neither may load or operate the selected raw driver under this contract.

## Supavisor transaction-pool selection

The future provider topology class is Supavisor transaction pooling. Direct PostgreSQL is limited to the local evidence baseline. Session pooling is limited to direct/session contamination fixtures. Retained artifacts must contain no endpoint hostname, URL, port, username, password, or project reference.

## Vercel Fluid Compute lifecycle

The intended future deployment is the Next.js Node.js runtime on Vercel Fluid Compute, with one process-global Pool per runtime instance. Future use of `attachDatabasePool` requires separate package, compatibility, lifecycle, and configuration approval.

## Reviewed candidate package versions

- Driver family: `pg`
- Reviewed candidate: `8.22.0`
- Possible type dependency: `@types/pg`
- Possible lifecycle dependency: `@vercel/functions`

No package installation or version range is authorized here.

## Final installation revalidation requirement

The package phase must revalidate the exact maintained release, dependency graph, types, Node compatibility, advisories, install behavior, license, bundle impact, and lockfile delta. Any approved installation must use an exact version without range operators.

## Local max=1 versus Production capacity policy

`max=1` is reserved for deterministic local evidence. It is not a Production setting. The Production maximum remains unfrozen until a reviewed budget accounts for provider client limits, provider backend limits, maximum concurrent Vercel instances, pool size per instance, and reserved administrative capacity.

## Unnamed-query policy

Named prepared statements are prohibited. Query configuration must not contain `name`. No contract may assume persistent prepared state across transaction-pool backend assignments. Borrower-created persistent prepared statements are violations.

## One-client-per-transaction rule

Each command checks out exactly one client, issues explicit `BEGIN`, executes every command statement on that client, and reaches proven `COMMIT` or `ROLLBACK` before normal release. Pool-level query helpers are prohibited for command transactions.

## Transaction-local role and context policy

Only reviewed transaction-local authority and context mechanisms are permitted. Tenant, branch, user, authorization, timeout, search path, and row-security context must be recomputed inside every transaction. No borrower context may exist after transaction end.

## Session mutation prohibitions

Production transaction-pool traffic must not use session `SET ROLE`, `SET SESSION AUTHORIZATION`, session GUCs, temporary objects, cursors, `LISTEN`, or session advisory locks. Arbitrary SQL, role names, function names, and identifiers from callers are prohibited. The transport exposes fixed domain commands only.

## Release and destroy state machine

Frozen states are `CHECKED_OUT`, `TRANSACTION_ACTIVE`, `COMMITTING`, `COMMITTED`, `ROLLING_BACK`, `ROLLED_BACK`, `CANCELLING`, `CANCELLED_ROLLBACK_PROVEN`, `UNKNOWN`, `DESTROYED`, and `RELEASED`.

Normal release is valid only from:

- `COMMITTED`;
- `ROLLED_BACK`;
- `CANCELLED_ROLLBACK_PROVEN`, after every sanitation observation passes.

`UNKNOWN`, rollback failure, cancellation uncertainty, sanitation failure, and socket, protocol, or identity uncertainty require destruction. Release from any other state is invalid.

## Timeout and cancellation policy

Database statement timeout, database lock timeout, driver/query timeout, harness process timeout, and external request timeout are distinct bounded classes. Transaction-local database timeouts are established first. Driver and harness deadlines exceed the intended database deadline by a bounded reviewed margin. Cancellation is attempted at most once. The harness then awaits query settlement, attempts rollback, verifies clean state, and releases only when cleanliness is proven; otherwise it destroys the client.

## TLS and credential boundary

Only a dedicated least-privilege LOGIN may be used. `postgres`, Supabase `service_role`, browser-readable secrets, and `NEXT_PUBLIC_*` database credentials are prohibited. Verified TLS is mandatory. Raw URLs, credentials, JWTs, tokens, and secret context values must not enter logs or retained evidence. Rotation behavior remains a provider gate.

## Provider evidence requirements

Provider approval requires explicit-transaction backend pinning, reset behavior, cancellation and disconnect outcomes, client and backend limits, pool observability, TLS behavior, credential rotation behavior, and proof that the total connection budget preserves administrative capacity.

## Binary and text decoding gate

No Core V2 field may rely on an unreviewed default parser. The package/evidence phases must freeze exact OID handling, text versus binary behavior, integer precision, timestamp precision, byte handling, nullability, row shape, and failure behavior before application integration.

## Harness-only status

This amendment authorizes non-executable contract artifacts only. It does not authorize package installation, executable harness code, executable SQL, database/provider contact, credentials, application routes, runtime integration, or Production use.

## PostgREST evidence boundary

Supabase JS/PostgREST remains the active AFEX application architecture. PostgREST owns its database sessions and transaction lifecycle. PostgREST evidence cannot substitute for raw-driver checkout, return, destruction, reuse, or session-sanitation evidence.
