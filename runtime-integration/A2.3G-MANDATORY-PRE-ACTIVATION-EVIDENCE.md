# A2.3G Mandatory Pre-Activation Evidence

Every item is mandatory and must be normalized, hashed, reviewed, and mapped to G1–G12. Provider statements do not replace required runtime tests.

## Provider and topology proof

- Supabase confirmation that a dedicated custom LOGIN is supported for the intended hosted topology.
- Supabase confirmation that SET-only membership with SET=true, INHERIT=false, ADMIN=false is supported.
- Confirmation and isolated proof that an explicit multi-statement transaction remains on one backend.
- Confirmed `SET ROLE` and `SET LOCAL ROLE` behavior for a NOINHERIT login, including `session_user`/`current_user` semantics.
- Confirmed cleanup after commit, rollback, statement timeout, cancellation, abrupt disconnect, and backend return/reuse.
- Confirmed transaction-level advisory-lock behavior; session-level locks must not be relied upon.
- Prepared-statement restrictions for the selected pooling mode and client.
- Vercel outbound PostgreSQL TCP, IPv4/IPv6, function region, runtime mode, lifecycle, duration, memory, and scaling evidence.
- TLS requirement, certificate/hostname validation behavior, and an approved secure network path.

## Capacity and lifecycle proof

- Current Production database connection usage and reserved/system capacity.
- Expected average/peak POS order rate and concurrent submissions.
- Supported maximum per-instance pool size and maximum instance behavior.
- Reviewed global connection budget with headroom and fail-closed exhaustion behavior.
- Production-only credential scope, encrypted delivery, rotation cadence, overlap procedure, emergency revocation, redeployment behavior, and Preview exclusion.

## Database identity attestation

- Dedicated LOGIN exists only after reviewed manual SQL execution.
- Exact role attributes and no unintended memberships, ownership, schema, table, sequence, function, or default privileges.
- Exact SET-only edge to `afex_core_runtime`; no INHERIT or ADMIN option.
- Only the intended LOGIN can assume Runtime; Runtime retains only the approved P2D.20 EXECUTE grant.
- Revocation/rollback and postcondition attestation complete successfully without recording a password or secret.

## Isolated runtime tests

- Identity before, during, and after activation.
- Sequential and concurrent backend-role contamination tests.
- Commit, forced rollback, timeout, cancellation, abrupt disconnect, and failover cleanup.
- Same-key retry and replay after unknown commit outcome; no new key and no duplicate financial effect.
- Transaction advisory-lock and concurrent first-acquisition behavior.
- Prepared-statement behavior under the selected client/mode.
- Pool exhaustion, shutdown, connection destruction/quarantine, expired credential, rotated credential, and revoked membership.

## Operational and Production-disabled evidence

- Sanitized correlation, connection, pool, timeout, cancellation, identity, latency, and error evidence with retention and alert ownership.
- Reviewed runbook, stop conditions, rollback/revocation, and decision authority.
- A disabled Production smoke test that proves configuration remains inactive and legacy behavior unchanged without creating a real order or calling P2D.20.
- Clean, reviewed source baseline and exact artifact hashes immediately before any activation decision.

Activation remains blocked until every applicable gate is `PROVEN`; partial, reported-only, conflicting, or missing evidence is insufficient.
