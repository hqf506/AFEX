## D. Cleanup Allowlist

The future execution allowlist is closed to these actions, each conditional on successful identity proof immediately before its action:

1. Stop only the exact verified immutable PgBouncer container ID. Compose project/service names, the Compose service selector, container name, and labels are evidence only and grant no stop or removal authority; no target is re-resolved from them after the accepted identity snapshot.
2. Remove only that exact same stopped and immediately reverified immutable PgBouncer container ID.
3. Disconnect only the verified `afex-a24e-pg17` container ID from the verified dedicated network ID, and only after the PgBouncer container is absent.
4. Remove only the verified `afex-pd6f-isolated` network ID after it has no endpoints and its ownership is independently proven.
5. Let the verified container-scoped tmpfs disappear as a consequence of container removal.

The default disposition of the image, repository files, evidence files, external secret file, Git branches/worktrees, and every volume is `RETAINED`. An unlabelled network, unknown volume, unexpected endpoint, unknown process, or recreated resource is excluded and is a blocker.

The allowlist never includes another container, a network without proven PD6F ownership, any Docker volume, another PostgreSQL instance, any Supabase resource, any general Docker resource, any image, any host file, any Provider/Vercel/Production resource, or anything selected by a wildcard. `docker system prune`, `docker volume prune`, `docker network prune`, `docker image prune`, broad `docker compose down`, directory deletion, globs, and delete-all operations are prohibited.

## E. Mandatory Pre-Cleanup Identity Gate

The future operator must capture a machine-readable before inventory and pass every check below without changing state:

1. Repository root, branch, worktree path, and clean status are exact; authority commit includes this reviewed contract and descends from `3c90ca74758f0511c2bdc10009bf15d618de39e8`.
2. Docker context name, endpoint, orchestrator, and daemon identity equal the separately approved local context. A remote context is prohibited.
3. The fixed Compose file, Dockerfile, and PgBouncer configuration hashes match their frozen values.

   The frozen values use one canonical byte domain: the committed file content encoded as valid UTF-8 without a byte-order mark, with LF line endings and its committed final newline preserved exactly. A future verifier reading a clean Windows worktree must operate on bytes, reject a UTF-8 BOM, invalid UTF-8, or any lone CR byte, replace each CRLF byte pair (`0D 0A`) with one LF byte (`0A`), retain every other byte including the final newline without decoding/re-encoding, and compute SHA-256 over that canonical byte sequence. Raw CRLF worktree SHA-256 is not authority and is never compared directly with the frozen hashes; a clean checkout does not fail solely because Git materialized CRLF. Worktree cleanliness remains a separate gate, and runtime container identity and configuration fingerprints remain independent evidence. PowerShell text pipelines, platform-default encoding, line-oriented reads, or transformations that add, remove, or synthesize a final newline are prohibited for this verification.
4. The container name resolves to exactly one ID. Its Compose project/service labels, image ID, configuration hash metadata, mounts, port binding, network ID, security settings, and running state match authority.
5. The actual Compose project label is exactly `pd6f-pooler`. Missing or different labels block cleanup; no project name is guessed.
6. The network name resolves to exactly one ID. Its driver, scope, labels, options, and complete endpoint set are recorded. Missing ownership metadata blocks network deletion.
7. The PostgreSQL name resolves to exactly one stable ID. Only its PD6F network attachment and alias may enter the allowlist; its full before fingerprint is retained to detect unintended mutation.
8. Every mount is classified as bind, tmpfs, named volume, or anonymous volume. Any volume or unexpected mount blocks cleanup.
9. Port `127.0.0.1:56432` is owned by the verified container publication. An unknown owner blocks cleanup and must not be killed.
10. Image consumers are inventoried. The image remains retained regardless of consumer count.
11. Accepted evidence files are hashed before cleanup without reading or retaining secret content. Repository and Git inventories are captured.
12. Immediately before every mutation, target ID, labels, consumer set, and configuration fingerprint are inspected again. Recreation or drift stops execution.

The gate must distinguish `ABSENT_ALREADY` from `OWNED_PRESENT`. An already absent resource is never recreated and is not treated as proof that an earlier cleanup was authorized. If ownership of any resource is not proven, that resource is excluded, the gate returns `NOT COMPLETED — CLEANUP IDENTITY GATE FAILED`, and no force or inference is permitted.

## F. Future Cleanup Command Contract

The following commands are specifications for a separately authorized future execution. They must not be run while creating or reviewing this contract. The values assigned to ID variables must come from the successful machine-readable identity snapshot and must be compared again immediately before use. Compose project/service identity and configuration remain evidence inputs only; they are never container mutation targets.

```powershell
$pd6gWorktree = (git rev-parse --show-toplevel).Trim()
$pd6gComposeFile = Join-Path $pd6gWorktree 'runtime-integration\pd6f-pooler\compose.yaml'
$pd6gComposeProject = 'pd6f-pooler'
$pd6gService = 'pd6f-pgbouncer'
$pd6gContainerId = '<IDENTITY_GATE_VERIFIED_CONTAINER_ID>'
$pd6gNetworkId = '<IDENTITY_GATE_VERIFIED_NETWORK_ID>'
$pd6gPostgresContainerId = '<IDENTITY_GATE_VERIFIED_POSTGRES_CONTAINER_ID>'

# STOP unless all ID variables are nonempty, contain no placeholder, belong to the accepted identity snapshot, and equal the immediately revalidated runtime IDs.
# STOP unless $pd6gContainerId still exists with the accepted ID, Compose project/service labels, image, mounts, port binding, network attachment and ID, configuration fingerprints, and running state; any recreation or replacement is an unexpected blocker and is never targeted.
docker stop $pd6gContainerId
# STOP unless that same $pd6gContainerId is stopped and its ID, labels, state, image, mounts, network attachment and ID, and configuration fingerprints are immediately revalidated without drift.
docker rm $pd6gContainerId
# STOP unless the accepted immutable $pd6gContainerId is absent by ID; a new container with the same name or labels is an unexpected recreation and is never targeted.
# PRE-DISCONNECT STOP: immediately revalidate the exact $pd6gPostgresContainerId and $pd6gNetworkId from the accepted snapshot, the single intended attachment and alias, unchanged PostgreSQL image/configuration/mounts/volumes/running state/restart count and all other attachments, absence of $pd6gContainerId, and absence of any unexpected consumer or recreation.
docker network disconnect $pd6gNetworkId $pd6gPostgresContainerId
# POST-DISCONNECT STOP: before any network removal, prove the same PostgreSQL container ID remains running with unchanged image, configuration, mounts, volumes, restart count, and all non-PD6F attachments; prove only the intended attachment is absent and that no stop, restart, recreation, or reconfiguration occurred.
# PRE-NETWORK-REMOVE STOP: proceed only after the post-disconnect checkpoint succeeds, then immediately revalidate the immutable network ID, ownership metadata, unchanged configuration, and complete endpoint inventory with zero consumers; recreation or metadata drift blocks removal.
docker network rm $pd6gNetworkId
# STOP unless the accepted immutable network ID is absent and the PostgreSQL and all non-target invariants remain unchanged.
```

The literal placeholders are not executable authority. A future reviewed execution package must substitute only the IDs captured by its machine-readable gate, must reject placeholder or empty values, must reject any value absent from the accepted snapshot or different from the immediately revalidated runtime ID, and must show the fully materialized commands before execution. No mutation may begin until those guards pass. Container removal has no force option and is authorized only for the same verified, already stopped immutable container ID.

Action classes and disposition:

1. **Stop/terminate:** bounded stop by the single verified immutable container ID only. Compose labels and configuration are evidence, not mutation scope. Failure stops the phase.
2. **Container removal:** removal by that same immutable container ID, without force, only after stopped-state and immediate ID/label/configuration revalidation.
3. **Network removal:** targeted disconnect by the verified network and PostgreSQL container IDs only after the independent pre-disconnect checkpoint; network removal is blocked until the PostgreSQL post-disconnect checkpoint succeeds and the network is immediately revalidated with proven ownership and zero consumers.
4. **Volume removal:** none authorized because no volume is part of the reviewed topology.
5. **Image treatment:** retain; no remove, prune, rebuild, or retag.
6. **Temporary-file treatment:** container tmpfs disappears with its container; runner temporary files are inventory-only blockers and are never glob-deleted. Repository, evidence, secret, branch, and worktree files remain untouched.

`docker compose down` is prohibited because the external network lifecycle and shared PostgreSQL attachment require separate identity-controlled actions, and because a broad project-down command obscures per-resource stop evidence.

## G. Post-Cleanup Absence Evidence

The future phase must retain separate, redacted, machine-readable before inventory, command results, after inventory, and disposition manifest. Each record must include schema version, authority commit, Docker context fingerprint, timestamps in UTC, bounded exit codes, inspected IDs, hashes, and per-resource status without secrets or raw environment values.

The after evidence must prove:

- the allowlisted container ID, exact name, and verified PD6F Compose labels are absent;
- no resource remains under the verified Compose project/service label pair;
- the dedicated network ID and name are absent only if its removal was authorized and completed;
- no Docker volume was removed and no unexpected volume exists in the PD6F topology;
- no listener owned by the removed PD6F container remains at `127.0.0.1:56432`;
- no PD6F-owned running container or process remains; unknown owners are reported rather than terminated;
- the verified PostgreSQL container still exists and its non-PD6F configuration, host publication, restart count, and running state are unchanged, while only the verified PD6F network attachment is absent;
- the pre-disconnect record proves the exact PostgreSQL container ID, network ID, intended attachment and alias, complete attachment set, image, configuration, mounts, volumes, running state, and restart count immediately before disconnect;
- the post-disconnect record proves that the exact PostgreSQL container remained running without restart, recreation, reconfiguration, image/mount/volume change, or change to any other network attachment, and that only the intended PD6F attachment became absent before network removal;
- network-removal evidence proves that the PostgreSQL post-disconnect checkpoint passed first and that the immutable network ID, ownership metadata, and zero-consumer inventory were revalidated immediately before removal;
- unrelated containers, networks, volumes, images, and their immutable IDs match the before inventory;
- the retained PgBouncer image disposition is explicit and its ID is unchanged;
- repository/worktree/branch status and tracked file hashes are unchanged;
- accepted PD6C and PD6F evidence files remain available with their accepted sizes and SHA-256 values;
- no secret content, DSN, credential, token, or raw environment value appears in evidence;
- every resource has exactly one disposition: `REMOVED`, `DISCONNECTED`, `RETAINED`, `ABSENT_ALREADY`, or `BLOCKED`.

Absence must be proved by ID and complete filtered inventory, not by a successful command exit or name lookup alone. The before/after inventories must make unintended removals mechanically detectable.

## H. Atomic Failure and Stop Rules

Execution stops before the first mutation for any ownership mismatch, unexpected resource consumer, shared or unknown network/volume, Docker context mismatch, missing required label, ambiguous Compose project, changed configuration fingerprint, unknown running container, unexpected port owner, unapproved mount, evidence-hash mismatch, or target wider than the allowlist.

Execution also stops between mutations if a resource is recreated, an ID or label changes, a consumer appears, a command fails, absence cannot be proven, or the materialized next command differs from the reviewed target. No automatic retry, force escalation, alternate project name, name-only deletion, prune, or compensating deletion is allowed.

Failure of any pre-disconnect or post-disconnect PostgreSQL invariant returns `PARTIALLY COMPLETED — CLEANUP STOPPED`. Network removal is prohibited, and no automatic repair, reconnect, retry, or additional mutation is allowed without new authorization. A replacement container or network is never adopted as the target.

Failure after any mutation is atomic authority failure even if earlier targets were removed. It returns:

`PARTIALLY COMPLETED — CLEANUP STOPPED`

The operator records the completed actions and current inventory, performs no repair or additional deletion, and waits for new authorization.

## I. Acceptance Gate

The only future success marker is:

`A2.5-PD6G CLEANUP COMPLETE — ABSENCE PROVEN`

It may be issued only when:

1. The pre-cleanup identity gate passed completely.
2. Only explicitly authorized and fully materialized commands ran.
3. Every resource required to be absent is absent by ID and inventory.
4. The PostgreSQL network attachment required to be disconnected is absent without other PostgreSQL mutation.
5. The independent PostgreSQL pre-disconnect and post-disconnect checkpoints passed, and network removal began only after the post-disconnect checkpoint and immediate zero-consumer/ownership revalidation succeeded.
6. All non-target resources are proven unchanged.
7. Retained evidence and repository sources remain byte-for-byte unchanged.
8. No mismatch, unexpected consumer, unknown removal, or unresolved partial state exists.
9. Complete redacted evidence and per-resource dispositions are independently reviewed.
10. Safety accounting matches actual commands and reports zero Provider, Vercel, Production, database, SQL, runner, and evidence-generation actions.

Failure decisions are exact:

- `NOT COMPLETED — CLEANUP IDENTITY GATE FAILED`
- `PARTIALLY COMPLETED — CLEANUP STOPPED`
- `CLEANUP EXECUTED — ABSENCE NOT PROVEN`

No failure decision permits continued cleanup.
