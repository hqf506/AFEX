# A2.4B.2 Direct-EXECUTE Architecture Decision

Status: ADOPT_DIRECT_EXECUTE_LOGIN_MODEL

## Decision

Adopt architecture B: a dedicated server-only application LOGIN receives direct EXECUTE only on:

`public.acquire_atomic_order_command_v1(uuid, uuid, uuid, text, text, text, text, timestamp with time zone)`

The LOGIN receives no membership in `afex_core_runtime`, performs no role switching, owns no object, and receives no direct relation, column, sequence, schema-CREATE, or generic function privilege. `service_role` remains rejected.

## Architecture comparison

| Dimension | A: SET-only membership plus local role | B: direct exact-signature EXECUTE | Decision basis |
|---|---|---|---|
| Least privilege | LOGIN can reach an intermediate privilege bundle through membership | LOGIN has one explicit callable capability | B has the smaller application privilege graph |
| Static privilege graph | LOGIN → membership → runtime role → function | LOGIN → exact function signature | B is simpler to attest and revoke |
| RLS | SECURITY DEFINER owner behavior is reached after role activation | Same SECURITY DEFINER owner behavior is reached directly | Equivalent only if function safety and FORCE RLS contracts remain exact |
| SECURITY DEFINER | Entrypoint remains the privileged boundary | Entrypoint remains the privileged boundary | B does not add another privileged function |
| Function-owner blast radius | Controlled by owner and function body in both models | Controlled by owner and function body in both models | Mandatory owner/body/ACL review remains |
| Privilege escalation | Role target and membership semantics add paths | No caller-selected role or membership path | B removes a class of escalation and contamination risk |
| Auditability | Requires membership and role-transition evidence | Exact direct function ACL is sufficient for caller privilege | B is easier to enumerate |
| Revocation | Revoke membership and credential | Revoke exact EXECUTE and disable credential | B is more direct and independently testable |
| Credential rotation | Same dedicated LOGIN lifecycle | Same dedicated LOGIN lifecycle | No material difference |
| Supavisor compatibility | Depends on undocumented role-state behavior | Requires ordinary function execution only | B removes the undocumented role-switch dependency |
| Connection contamination | Role residue is a critical risk | No role transition exists; general transaction/session residue remains | B materially narrows risk |
| Cancellation/unknown outcome | Still unresolved | Still unresolved | Both require identical fail-closed tests |
| Replay/executor compatibility | P2D.20 output contract unchanged | P2D.20 output contract unchanged | B preserves acquisition/replay semantics |
| Operations and maintenance | Membership, activation, reset, and ACL units | LOGIN, exact ACL, function contract, and revocation units | B is simpler |

## Evidence taxonomy

### Documented facts

- PostgreSQL supports exact function-signature EXECUTE ACLs and SECURITY DEFINER execution.
- Supabase guidance aligns tightly scoped SECURITY DEFINER functions with explicit EXECUTE grants and revocations.
- Transaction-pool mode does not support persistent prepared statements.
- Supabase does not formally guarantee the role-switch/reset semantics required by architecture A.

### Project-specific inference

- A single direct EXECUTE edge is less privileged and more auditable than a membership plus role-transition edge for this one-entrypoint application.
- Removing role switching reduces contamination and operational failure modes without changing P2D.20 business behavior.

### Unresolved runtime facts

Transaction-pool execution, cancellation, ambiguous outcomes, transaction advisory locks, connection quarantine, capacity, TLS, credential revocation, ACL revocation, denial of other objects, and observability still require attestation or isolated testing.

## Conditions of adoption

Adoption is architectural only. It does not authorize SQL, credentials, package installation, database access, application wiring, P2D.20 invocation, deployment, or activation. The frozen function safety contract and exact result/input contracts remain unchanged.
