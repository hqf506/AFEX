## POS trace from final button

1. **UI state.** `app/pos/sale/checkout/page.tsx:180-257` restores customer and item drafts from local storage. Active POS employee is read from the client POS session, and branch selection resolves from POS employee or authenticated profile (`:180-188`).
2. **Runtime prerequisites.** Discounts and VAT are loaded from `GET /api/pos/runtime` with a client resource cache (`:259-338`).
3. **Submit guard.** `handleCreateInvoice` uses both React loading state and `submitLockedRef` to reject duplicate taps (`:454-465`). This is UI protection, not durable exactly-once proof.
4. **Client validation.** `useInvoiceCheckout.createInvoice` checks customer, items, branch, payment, and online status (`hooks/use-invoice-checkout.ts:222-316`).
5. **Stable attempt key.** `getOrCreateClientIdempotencyKey` retains one key in a ref until checkout is cleared (`:214-219`, `:282`). Offline drafts persist that key.
6. **Request.** The hook posts customer, employee, branch, payment snapshot, discount, tax, note, and items to `/api/orders` (`:318-339`). These are untrusted browser claims.
7. **Authentication.** `handleCreateOrderPost` calls `requireApiAuth` for admin/employee/cashier (`app/api/orders/route.ts:686-696`). `requireApiAuth` delegates to `requireAuthorizationContext`, which calls `auth.getUser`, loads the active profile, and derives tenant/branch capability (`lib/authorization-context.ts:150-318`).
8. **Request normalization.** Route parses payment, key, employee, branch, and item identifiers (`app/api/orders/route.ts:698-740`).
9. **Privileged client.** Route constructs a service-role SDK client (`:753-773`). It derives tenant from the authenticated profile or a server-side profile lookup (`:774-796`); the browser tenant is not accepted.
10. **Feature and scope checks.** Orders/POS feature states, required branch, profile branch, branch ownership, employee identity, and catalog evidence are checked before mutation (`:798-1136`). Employee resolution may query both `profiles` and `pos_profiles`.
11. **Idempotency pre-resolution.** `createIdempotencyService` builds a scoped command identity. Future reads are optional; legacy fallback queries `orders.client_idempotency_key` (`lib/idempotency/service.ts:267-481`). Errors are fail-closed at the route.
12. **Legacy transaction.** The route calls `create_invoice_with_items_safe` with the service-role SDK (`app/api/orders/route.ts:1164-1184`). The database function is the only proven transaction boundary for customer/order/invoice/items and its legacy inventory behavior. The route itself does not own that transaction.
13. **Unknown outcome recovery.** On RPC transport/error paths, the same key is resolved through the idempotency service (`:1186-1237`). The route does not blindly issue a new key.
14. **Post-RPC blocking writes.** Payment snapshot, order employee patch, invoice-item lookup, and inventory actor patch run in parallel branches (`:1289-1397`). They are separate transactions from order creation. Audit persistence then blocks the HTTP response (`:1399-1419`). A successful legacy order can therefore coexist with failed adjunct state.
15. **After-response work.** Cost snapshot and PDF/WhatsApp delivery use Next.js `after()` (`:1421-1468`, `:1486-1518`). They are not part of order atomicity. Exact provider delivery guarantees are outside this route.
16. **Response/UI transition.** Success returns order/invoice identifiers (`:1470-1473`). The hook clears catalog cache, builds the success snapshot, clears drafts, stores the snapshot in session storage, and navigates to `/pos/sale/success` (`hooks/use-invoice-checkout.ts:361-391`; checkout page `:348-363`).
17. **Receipt/follow-up.** Success page reads the snapshot, renders/prints the receipt, and offers navigation (`app/pos/sale/success/page.tsx:292-520`). WhatsApp was already scheduled server-side; the page does not establish delivery atomicity.

## Failure and retry behavior

- Duplicate taps are blocked locally, while durable protection depends on the stable client key and database behavior.
- Offline submission saves a draft instead of mutating the database.
- Network/parse failures show an uncertain-submission message and retain the key for the attempt.
- A response timeout after database commit is an unknown outcome; safe recovery must resolve the same key.
- Legacy and optional future idempotency readers coexist today. That is not permission to dual-write.
- Customer creation is coupled inside the legacy RPC for order submission; standalone customer APIs also exist. Future acquisition must freeze the customer intent without performing a second customer write.

## Atomicity conclusion

Only the internal work of `create_invoice_with_items_safe` can be described as one database-function transaction. Payment persistence, employee attribution, inventory attribution, audit, cost snapshot, PDF, and notifications are outside that transaction. Current Production behavior is preserved during A2.2; no claim is made that the end-to-end route is atomic.
