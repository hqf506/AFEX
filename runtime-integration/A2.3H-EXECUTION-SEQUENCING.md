# A2.3H Execution Sequencing

## Required sequence

1. **A2.3H.1 — Submit provider questions**
   - Operator reviews redaction, submits the exact scoped questions, and records safe case metadata.
   - No database or Runtime action.

2. **A2.3H.2 — Normalize responses**
   - Preserve, redact, hash, classify, map to gates, and reconcile contradictions.
   - Do not skip this step or infer Runtime proof.

3. **A2.3H.3 — Design complete test SQL and harness**
   - Produce complete role, LOGIN, membership, harmless-function, attestation, cleanup SQL and a bounded test harness.
   - No execution, credential, Production business object, P2D.20 call, or arbitrary query interface.

4. **A2.3H.4 — Independent SQL and harness review**
   - Review PostgreSQL compatibility, ownership, privileges, search path, cleanup, redaction, concurrency, and fail-closed behavior.
   - Freeze hashes and an execution manifest.

5. **A2.3H.5 — Operator executes isolated tests**
   - User manually executes only the approved package in the isolated environment.
   - Capture evidence, stop on first blocking mismatch, and complete cleanup/attestation.

6. **A2.3H.6 — Final architecture approval**
   - Reconcile provider and Runtime evidence, update G1–G12, and select or reject the transaction-pool architecture.

## Project rules

- Codex does not execute SQL.
- Complete SQL is printed for review; the user returns it for independent review and executes manually only after approval.
- No Production business writes, application routes, P2D.20 invocation, package installation, feature activation, `service_role` fallback, or dual write.
- No fallback to legacy after an uncertain Core V2 send.
- Every phase begins from a clean reviewed tree and uses explicit path-scoped commits only when separately authorized.

Skipping response normalization, independent review, cleanup attestation, or final gate review invalidates approval.
