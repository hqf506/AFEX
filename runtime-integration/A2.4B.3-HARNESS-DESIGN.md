# A2.4B.3 Harness Design

Status: SOURCE-CORRECTED; RUNTIME UNPROVEN; EXECUTION NOT AUTHORIZED

The standalone Node harness is server-only by placement, has no application import, exports no query capability, accepts no SQL or object target, and contains only fixed unnamed statements. It cannot call P2D.20 or read business data.

## Hard-disabled configuration

Execution requires the exact authorization literal, a dedicated test URL, an explicit Transaction Pooler endpoint class, approved host suffix and port, exact TLS-mode input, bounded controller/lock/checkout timeouts, approved dependency-version evidence, and an ignored run directory. Loopback requires a separate exact local-simulation literal. The URL and hostname are never emitted; topology evidence contains only class, port, TLS mode, a host digest, and an explicit statement that certificate verification is not proven by source.

## Assertions and lifecycle

Every implemented case uses centralized assertions and returns `PASS`, `FAIL`, or `INCOMPLETE`. Identity is asserted before and after BEGIN, COMMIT, and ROLLBACK. Probe caller/definer identities, backend PIDs, exact denial SQLSTATE `42501`, timeout SQLSTATE `57014`, lock contention/release, unnamed-statement state, sequential identity, and concurrent distinct-client isolation are asserted. A client is destroyed after any uncertain error.

## Controllers

- Implemented in source: two-client advisory-lock contention, bounded timeout/quarantine, bounded pool exhaustion, sequential contamination, and concurrent isolation.
- Fail-closed executable descriptors: cancellation, abrupt disconnect, unknown outcome, LOGIN disablement, and EXECUTE revocation.
- LOGIN disablement and EXECUTE revocation remain provider-blocked external mutation phases.

Any placeholder makes the final result `INCOMPLETE` and the process exit nonzero. Runtime proof remains absent until a separately authorized isolated execution.
