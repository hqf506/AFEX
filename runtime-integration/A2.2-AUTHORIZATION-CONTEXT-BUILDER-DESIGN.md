# A2.2 Authorization Context Builder Design

Status: design only; blocked from implementation

## Trust rule

The browser may propose business intent but cannot assert actor, tenant, branch authority, role, capability, POS identity, canonical bytes, fingerprint, correlation authority, or retention policy. The future builder is server-only and consumes the verified user-context client; it does not consume the service-role client as authority.

## Field provenance matrix

| Field | Accepted input | Authoritative derivation | Database revalidation | Browser trust |
|---|---|---|---|---|
| Authenticated actor ID | Auth cookie/JWT transport only | `auth.getUser()` on server | P2D.20 trusted evidence | Prohibited as a body field. |
| Effective employee/cashier ID | Optional browser POS-session hint | Server reads active `profiles`/`pos_profiles`, tenant, branch, status, and actor relationship | P2D.20 derives/validates actor evidence | Hint only; never trusted. |
| Tenant ID | None | Active authenticated profile | Required | Prohibited. |
| Branch ID | Requested branch hint where product permits | Server profile assignment plus tenant-owned branch verification; system admins still require explicit valid branch | Required | Hint only. |
| User role/capabilities | None | Active server profile and frozen role mapping | Database uses trusted evidence, not browser role | Prohibited. |
| POS PIN actor | PIN result reference/employee hint | Actor-scoped PIN verification followed by fresh server-side employee lookup | Required | PIN and stored client session are insufficient alone. |
| Correlation reference | Optional sanitized inbound request ID | Server validates allowlist or generates UUID | Stored/bound by acquisition | Browser value may be accepted only as trace input, never authority. |
| Request ID | Transport header | Server validates or generates; unique per HTTP attempt | Not an idempotency identity | Not authoritative. |
| Client idempotency key | Stable opaque value created at checkout start | Server validates length/format; preserves across retries | P2D.20 hashes and scopes it | Untrusted but required as stable identity. |
| Canonical payload | Business intent | Server validates A1/P2D.18A contract and canonicalizes deterministically | P2D.20 revalidates canonical contract | Raw browser JSON is never hashed directly. |
| Fingerprint projection | None | Server derives from canonical validated intent | P2D.20 independently derives/checks | Prohibited. |
| Retention timestamp | None | Server policy from accepted time and frozen retention bounds | P2D.20 validates | Prohibited. |

## Builder phases

1. Validate authenticated user using the request-bound user client.
2. Load a fresh active profile; reject absent tenant or invalid role.
3. Resolve branch scope from server evidence; never merge mismatched tenant inputs.
4. Resolve POS employee through actor-scoped verification and fresh server data.
5. Check required application capability (`orders:write` and POS access where applicable).
6. Validate business intent against A1 and P2D.18A without mutation.
7. Derive canonical payload, fingerprint projection, retention, correlation, and command metadata.
8. Produce a sealed request-local value accepted only by the narrow trusted client facade.

The existing `requireAuthorizationContext` is useful input evidence but is not itself the P2D.20 database authorization context. Its current `posEmployee` starts null and its verifier accepts an employee ID hint; future use must call and bind the verified result before acquisition.

## Failure contract

The builder returns only stable categories: authentication required, actor inactive, actor unauthorized, tenant unavailable/mismatch, branch unavailable/mismatch, POS actor invalid, invalid command, canonicalization failure, and internal invariant violation. Raw Supabase errors, SQLSTATE details, payloads, PINs, tokens, and secrets are never returned or logged.

## Request-local integrity

- No module-global authority cache.
- No acceptance of a context built for another request, actor, tenant, or branch.
- No mutable public fields after sealing.
- Abort before trusted-client acquisition if authentication changes or evidence expires.
- Correlation and request IDs are distinct from idempotency identity.
- Canonical payload and projection are derived once from the same validated value and passed without reconstruction.

## A1 preservation

The builder must import or reproduce no alternate payload, error, response, performance, security, authorization, idempotency, or replay contract. Any mismatch with A1 is a release blocker requiring a separately reviewed contract amendment—not local coercion.
