# AFEX ERP / POS — A2.1R Runtime Privilege Evidence Plan

Status: DESIGNED — NOT REVIEWED FOR EXECUTION — DO NOT RUN

## 1. Purpose

This package is a read-only Production evidence design for A2 decision
`A2D-001`. It determines whether a dedicated managed LOGIN can safely establish
`afex_core_runtime` and invoke only installed P2D.20 without direct object access
or broader Runtime authority.

It does not create or repair the LOGIN, change membership, establish a role,
invoke P2D.20, inspect business rows, or prove application pool behavior.

Execution requires separate approval after independent security, functional, and
performance review of the complete SQL and runner.

## 2. Evidence questions

The package inventories:

1. candidate managed LOGIN existence and exact role attributes;
2. direct and transitive memberships, options, grantors, and role paths;
3. every role the candidate can establish with `SET ROLE`;
4. exact `afex_core_runtime` properties, members, parents, and settings;
5. P2D.20 identity, owner, SECURITY DEFINER state, fixed configuration, and ACL;
6. effective execution of every public function and SECURITY DEFINER function;
7. table/view, column, sequence, and schema privilege surfaces;
8. access to non-public and sensitive Supabase schemas;
9. object ownership or settable-owner exposure;
10. RLS, FORCE RLS, superuser, BYPASSRLS, and ownership bypass paths;
11. default ACL and PUBLIC-derived privilege sources;
12. objects owned by `afex_function_owner`;
13. possible legacy write-function exposure using a review-only name heuristic;
14. direct/effective Core V2 ledger, payload, and outbox access;
15. role/database GUCs affecting search path, role, RLS, timeout, application
    name, or authorization-context custom settings; and
16. whether catalog evidence supports the trusted-client proposal.

No catalog can prove how an unknown application driver or pool resets session
state. Unless separately reviewed pool evidence exists, the final safe database
classification remains `POOLING_MODEL_UNRESOLVED` after all catalog checks pass.

## 3. Target-role strategy

### Explicit mode

The operator supplies a role through runner parameter `-TargetRole` or environment
variable `AFEX_CORE_V2_RUNTIME_LOGIN`. The role must match PostgreSQL unquoted
identifier syntax and is passed as a safely quoted psql variable.

### Discovery mode

An empty target lists non-system, non-superuser LOGIN roles that have at least
one of:

- direct membership in `afex_core_runtime`;
- effective ability to `SET ROLE afex_core_runtime`; or
- direct/PUBLIC P2D.20 EXECUTE evidence.

Discovery never silently chooses a candidate. Zero candidates classifies
`LOGIN_MISSING`; multiple candidates classify
`MULTIPLE_AMBIGUOUS_LOGIN_CANDIDATES`.

## 5. Decision classifications

| Classification | Interpretation |
|---|---|
| `READY_AS_DESIGNED` | Database and independently reviewed pool evidence both satisfy the design. The catalog-only run does not claim this by itself. |
| `READY_WITH_CLOSURE_REQUIRED` | Core design is viable, but non-critical excess role attributes/configuration require externally reviewed closure. |
| `LOGIN_MISSING` | No intended candidate exists. |
| `MULTIPLE_AMBIGUOUS_LOGIN_CANDIDATES` | Discovery cannot identify one authoritative LOGIN. |
| `ROLE_GRAPH_UNSAFE` | Membership count/options or SET ROLE reachability exceeds the contract. |
| `EXECUTE_SURFACE_TOO_BROAD` | P2D.20 is unavailable as intended or another public function is executable. |
| `DIRECT_OBJECT_ACCESS_UNSAFE` | Candidate/runtime can own, create, or directly/effectively access prohibited objects. |
| `RLS_BYPASS_RISK` | Candidate/runtime is superuser, BYPASSRLS, or otherwise has an owner bypass. |
| `POOLING_MODEL_UNRESOLVED` | Catalog contract is otherwise viable, but session/pool reset evidence is absent. |
| `INSUFFICIENT_EVIDENCE` | Required role/function/catalog evidence is unavailable. |

Section 260 uses a fixed severity order and emits detailed booleans alongside the
single classification. Detailed result sets remain authoritative for review; a
classification never authorizes implementation by itself.

## 6. Sensitive-output policy

Allowed restricted evidence:

- role names/OIDs and safe attributes;
- membership graph/options/grantors;
- schema/object/function names and signatures;
- owners, ACL metadata, RLS/policy posture, and GUC names/values;
- stable classification and completion markers.

Forbidden output:

- passwords or password hashes;
- connection strings, URLs, JWTs, keys, and credentials;
- table rows or customer/order/payment data;
- raw function execution results;
- P2D.20 acquisition output;
- secrets or environment values.

Evidence is operationally restricted, stored under the ignored P2D `evidence/`
path, and must not be staged or committed.

## 7. Runner behavior

The PowerShell runner:

- reads the connection URL only from `SUPABASE_DB_URL`;
- accepts an optional target role without inventing one;
- verifies the reviewed SQL SHA-256 and PostgreSQL 18.4 client;
- parses host/port/database/user without placing the URL or password in process
  arguments;
- writes a temporary PGPASSFILE with a current-user-only ACL;
- clears the connection URL before launching child `psql`;
- passes `ON_ERROR_STOP=1`, target role, and the SQL file;
- captures stdout and stderr separately;
- records UTC run ID, target mode/value, SQL/runner hashes, exit code, marker,
  evidence filenames, and cleanup result;
- treats a nonzero psql exit or missing marker as failure;
- preserves NOTICE/WARNING stderr as evidence;
- restores environment variables and removes the temporary pgpass in `finally`;
- reports cleanup failure separately without rewriting a successful SQL result;
  and
- never prints a URL, password, or pgpass contents.

## 8. Operator workflow after independent approval

Do not execute during A2.1R. After a separate approval:

1. Review the complete SQL, runner hash, catalog scope, and classification logic.
2. Confirm the P2D evidence directory remains ignored and empty of committed
   secrets.
3. Set `SUPABASE_DB_URL` only in the operator process.
4. Run discovery mode first without a target.
5. Review candidate count and restricted evidence.
6. If exactly one candidate is approved, rerun explicit mode with that exact role.
7. Verify psql exit code zero and marker
   `A21R_900_RUNTIME_PRIVILEGE_DIAGNOSTIC_COMPLETE`.
8. Hash and review stdout, stderr, and summary; do not commit them.
9. Submit complete evidence for security review.
10. Update A2D-001/A2D-002 only after database and pool/driver evidence agree.

The runner command is intentionally withheld from execution until this package
receives explicit approval.

## 9. Interpretation guide

- PUBLIC function EXECUTE may cause `EXECUTE_SURFACE_TOO_BROAD` even without an
  explicit grant; review the provenance inventory rather than assuming safety.
- Schema USAGE is reported separately from CREATE. CREATE is an unsafe object-
  creation capability; USAGE may still expose functions and must be correlated
  with function ACLs.
- Table ownership and superuser/BYPASSRLS can bypass ordinary RLS; FORCE RLS does
  not constrain superusers or BYPASSRLS roles.
- SECURITY DEFINER access is an intentional privilege amplification boundary and
  must be allowlisted by exact signature and fixed search path.
- A clean role graph does not prove pool cleanup. Driver session evidence remains
  mandatory before A2.5.

## 10. A2 implications

### A2.2 allowed before evidence

- adapter-only TypeScript contract types;
- client-port interfaces with no concrete driver or credential;
- private/public module topology declarations;
- stable scanner rules and isolated fixtures;
- bans on direct P2D.20, sealer, bytea normalizer, ledger, browser, and legacy
  fallback imports;
- no-activation and export-boundary tests.

### Blocked before evidence

- concrete client or credential contract tied to a role name;
- pool/session/SET ROLE implementation;
- environment variable names for a Production credential;
- P2D.20 invocation;
- raw driver form assumptions;
- sealer implementation or full authority retrieval;
- route/API/POS/Admin integration.

A2.5 remains fully blocked until the diagnostic evidence and independent pool/
driver evidence are reviewed. A2.6 additionally remains blocked by the separate
Authorization Context retrieval SQL-design gate.

## 11. Exact review gate

Before execution, an independent review must verify:

1. PostgreSQL 17.6 catalog/function compatibility;
2. every section is read-only and catalog-only;
3. candidate discovery cannot silently select a role;
4. ACL and PUBLIC provenance are not hidden;
5. classification ordering cannot produce a false ready result;
6. no business function is invoked;
7. the runner exposes no credential in arguments, output, errors, or evidence;
8. cleanup and SQL outcomes remain distinct; and
9. SQL and runner SHA-256 values match the reviewed files.

Only after that review may the operator request separate authorization to run the
diagnostic. A2.1R itself authorizes no connection or execution.

## 12. A2.1R.1 correction record

The corrected package applies one canonical target-candidate rule in explicit
and discovery modes. Discovery includes direct Runtime membership, effective
`SET ROLE afex_core_runtime`, and direct P2D.20 EXECUTE ACL provenance. Explicit
mode assesses the named role even when its current attributes violate the
intended LOGIN contract. Sections 020, 250, and 260 expose independently named
candidate counts; disagreement, a missing explicit target, or incomplete
assessment resolves to `INSUFFICIENT_EVIDENCE`.

Privilege evidence now separates the target's pre-SET state from the
`afex_core_runtime` post-SET state and reports direct-role, PUBLIC,
membership-derived, and ownership provenance. Function evidence also identifies
SECURITY DEFINER amplification. Relation, column, sequence, schema, function,
ownership, default-privilege, and RLS evaluation covers every non-system schema;
only `pg_*` and `information_schema` are excluded. This deliberately includes
Supabase-managed and extension schemas such as `auth`, `storage`, `vault`,
`realtime`, `graphql`, `net`, and `cron` when present.

The final decision uses the frozen severity order: insufficient evidence,
missing or ambiguous LOGIN, RLS bypass, unsafe role graph, unsafe direct object
access, broad EXECUTE surface, closure required, and unresolved pooling. Table
ownership without FORCE RLS, ability to SET ROLE to such an owner, and
unexpected SECURITY DEFINER amplification feed `RLS_BYPASS_RISK` directly.
P2D.20 is the sole approved executable Runtime function in this phase; the
allowlist must be changed through a separately reviewed contract revision.

The runner now has a validated 30–3600 second timeout with a conservative
300-second default. Timeout is a distinct `RUNNER_TIMEOUT` failure, terminates
the native process, preserves partial stdout/stderr, records the timeout and
native exit state, and still performs credential cleanup in `finally`.

Pooling remains unresolved by repository and catalog evidence. Transaction or
session pooling, `RESET ROLE`, `DISCARD ALL`, and connection-return sanitation
must be demonstrated separately before `READY_AS_DESIGNED` or any A2.5 work is
permitted.
