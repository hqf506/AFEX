# A2.1S — Future Migration and Attestation Plan

Status: NON-EXECUTABLE DESIGN

## Design principles

The future change is a forward-only, exact-object privilege closure with a
separate read-only attestation. It must not use schema-wide wildcard revocation,
alter managed ownership, or infer safety from names. All planned mutations stay
blocked until the open evidence gates are closed.

## Ordered migration units

### 1. Frozen-manifest preflight

Fail before mutation unless server identity, PostgreSQL version, UTF-8, exact
artifact hashes, transaction state, and expected P2D.19/P2D.20 identities match.
Capture exact OIDs, signatures, owners, ACL arrays, role attributes,
memberships, schema ACLs, default ACLs, policies, dependencies, and trigger
bindings into the reviewed evidence manifest.

### 2. Ownership verification

Prove `afex_function_owner` owns exactly P2D.20 and the canonicalizer in the
Core V2 scope; prove `afex_core_runtime` owns nothing. Verify managed objects
remain owned by their expected Supabase/extension owners. Any owner mismatch is
a STOP condition.

### 3. Role-attribute verification

Verify the exact frozen runtime attributes and role configuration. This unit is
verification only unless a separately reviewed role-normalization decision is
approved. Existing postgres/Supabase administrative membership is not changed.

### 4. Application membership closure

Only after the LOGIN and pooling design are approved, establish or verify one
LOGIN-to-runtime edge with administration false, inheritance false, and SET
true. Verify the LOGIN has no other SETtable role. No generic membership change
is permitted.

### 5. PUBLIC function closure

Use an explicit manifest of exact signatures owned by postgres/application
owners. Each entry requires caller inventory, SECURITY DEFINER review, trigger
or helper classification, and rollback ACL before-image. Managed-schema
functions are excluded unless their product-owner review separately approves
an exact change.

### 6. Direct ACL closure

Verify P2D.20 has exactly owner and runtime EXECUTE entries with no PUBLIC ACL.
Verify the canonicalizer remains owner-only. Remove only catalog-proven,
manifested direct runtime ACLs that are outside the allowlist. Current evidence
shows none beyond P2D.20.

### 7. Explicit allowlist grants

Materialize only the exact P2D.20 signature as caller executable. No helper,
replay, legacy, trigger, or managed function is added implicitly.

### 8. Schema closure

Preserve required `public` USAGE and deny CREATE. Do not change auth, storage,
realtime, extensions, graphql, vault, net, cron, or future managed schemas
without exact product evidence. Verify no direct runtime schema ACL exists.

### 9. Table and sequence closure

Verify zero runtime ownership and zero direct/effective mutation privilege for
all relations and sequences, with explicit emphasis on the context, command,
payload, ledger, outbox, order, payment, inventory, and customer surfaces.
Extension view findings require a separate supported ACL disposition.

### 10. Default-privilege closure

Evaluate exact owner/schema/object-type tuples. Change only a tuple whose owner
will create future Core V2 objects and whose before-image is frozen. Never alter
defaults globally or under a different owner identity.

### 11. Postcondition attestation

Run a separate read-only, fail-closed artifact after commit. It must compare
catalog state to the frozen manifest and emit one completion marker.

### 12. Rollback strategy

Before mutation, freeze every exact ACL and membership row required for
restoration. Rollback restores only changed ACL/membership tuples and verifies
their hashes. If a partial state commits, stop traffic from the future Core V2
LOGIN, preserve legacy behavior, and use a separately reviewed forward fix or
exact restoration package. Never rerun a one-time migration blindly.

## Migration STOP conditions

- Candidate LOGIN missing, ambiguous, managed by an unexpected owner, or able
  to SET ROLE beyond the allowlist.
- Pool/session reset evidence absent.
- Any runtime attribute, owner, OID, signature, ACL, policy, dependency, or
  trigger differs from the frozen preflight.
- An object is extension-, storage-, auth-, realtime-, or Supabase-managed and
  lacks product-owner approval.
- A PUBLIC ACL has unenumerated application consumers.
- Canonicalizer is directly executable by runtime or PUBLIC.
- Runtime owns an object or has a table/sequence mutation path.
- Rollback before-images or approval signatures are incomplete.

## Required attestation postconditions

1. Runtime attributes exactly match the frozen NOLOGIN/NOINHERIT contract.
2. Runtime owns no object and is a member of no parent role.
3. The approved LOGIN has exactly one SET-capable membership and no inherited
   runtime authority.
4. P2D.20 exact signature, owner, SECURITY DEFINER flag, fixed search path,
   source hash, result type, and dependency set match.
5. Runtime has direct EXECUTE only on P2D.20.
6. P2D.20 has no PUBLIC EXECUTE.
7. Canonicalizer remains owner-only and transitive-only.
8. No unexpected legacy or SECURITY DEFINER function is executable before or
   after SET ROLE.
9. Runtime has no direct or effective table, column, sequence, schema CREATE,
   ledger, payload, command, context, or outbox access.
10. Runtime cannot bypass RLS by attributes, ownership, SETtable owner, or an
    unexpected SECURITY DEFINER path.
11. RLS and FORCE RLS state on Core V2 tables is unchanged.
12. Managed object owners and ACLs excluded from the approved manifest are
    byte-for-byte unchanged.
13. Default privileges cannot broaden future runtime access.
14. Pool reset evidence proves no role or session-state leakage.
15. Legacy application behavior remains active and unchanged.

## Operations that are never generic

- Schema-wide revocation of function execution in `public`.
- Blanket privilege removal from `storage`, `auth`, `realtime`, `extensions`,
  `graphql`, `vault`, `net`, or `cron`.
- Default-privilege changes without exact owner and schema identity.
- Ownership changes to Supabase-, storage-, or extension-managed objects.
- Membership or ACL changes involving postgres, authenticator, service roles,
  Supabase administrative roles, browser roles, issuer roles, or workers without
  exact proof and separate approval.
- Name-pattern classification as authorization for mutation.

## Review and approval chain

Catalog evidence review → dependency/caller review → Supabase/extension-owner
review where applicable → pool design review → exact migration review →
rollback review → manual execution approval → post-install attestation →
runtime integration gate.
