# A2.5.PD.4B Cancellation and Real-Driver Contract Amendment

## 1. Status and scope

Status: **FROZEN**. This additive amendment governs the future real-driver adapter. It contains no executable implementation and does not alter the merged Fake Driver evidence. Its authoritative cancellation model is `COMBINED_SERVER_TIMEOUT_AND_DESTROY`.

Normative terms **MUST**, **MUST NOT**, **SHOULD**, and **MAY** have their usual requirements meaning. A conservative destroy is always permitted where reuse safety cannot be proved.

## 6. Cancellation model

The selected model is exactly **`COMBINED_SERVER_TIMEOUT_AND_DESTROY`**:

1. Inside every explicit transaction, the future adapter establishes bounded transaction-local server timeouts before business statements.
2. `SERVER_STATEMENT_TIMEOUT` is the authoritative active-query cancellation primitive. `SERVER_LOCK_TIMEOUT` may terminate lock acquisition earlier.
3. The adapter owns an `APPLICATION_DEADLINE` later than the server statement timeout. It is a safety watchdog, not proof of backend cancellation.
4. A normal server timeout is accepted only after the query completes its ordinary pg rejection path and a post-settlement transaction status is available. It requires rollback.
5. If the application deadline wins, or server settlement is not observed within the bounded grace, the adapter MUST destroy the client. It MUST NOT begin rollback on an unsettled protocol stream.
6. Driver `query_timeout` MUST be omitted/zero in Production because pg 8.22 rejects locally without sending a backend cancel and can obscure wire settlement.
7. Explicit driver/protocol cancel attempts are zero. Server timeout configuration is one per transaction policy establishment. Rollback attempts are at most one. Release/destroy calls are exactly one.

Rejected alternatives: there is no documented driver public cancel API; explicit CancelRequest would require private key/PID surfaces and unsafe physical-backend assumptions; server timeout alone lacks a client-side escape for connection failure; destroy alone sacrifices deterministic server-side termination; therefore neither alternative is sufficient.

## 7. Timeout taxonomy

| Class | Owner/source | Expected surface | Transaction consequence | Required action / retained code | Production |
|---|---|---|---|---|---|
| `POOL_CHECKOUT_TIMEOUT` | Pool pending-acquire use of `connectionTimeoutMillis` | Acquire rejects before ownership | No transaction | No rollback; `PG_POOL_CHECKOUT_TIMEOUT` | Authorized |
| `CONNECTION_ESTABLISHMENT_TIMEOUT` | pg connection timer | Connect rejects/stream destroyed | No usable transaction | Destroy/remove; `PG_CONNECTION_TIMEOUT` | Authorized |
| `SERVER_LOCK_TIMEOUT` | PostgreSQL transaction-local policy | SQLSTATE `55P03` | Usually failed transaction | Settle, rollback; `PG_LOCK_TIMEOUT` | Authorized |
| `SERVER_STATEMENT_TIMEOUT` | PostgreSQL transaction-local policy | SQLSTATE `57014` | Failed transaction | Settle, rollback; `PG_STATEMENT_TIMEOUT` | Authorized |
| `APPLICATION_DEADLINE` | Adapter monotonic timer | Adapter event | State uncertain until ordinary settlement | Destroy if it wins; `PG_QUERY_SETTLEMENT_UNKNOWN` | Authorized |
| `DRIVER_QUERY_TIMEOUT` | pg local query timer | local `Query read timeout` rejection | Backend may still execute | Destroy; `PG_QUERY_TIMEOUT_LOCAL` | Prohibited as primary; omit/zero |
| `IDLE_IN_TRANSACTION_TIMEOUT` | PostgreSQL | server termination/error | Connection unusable/uncertain | Destroy; `PG_CLIENT_ERROR` or connection category | Defense only, never workflow control |
| `CANCEL_SETTLEMENT_TIMEOUT` | Adapter post-deadline grace | No ordinary settlement in grace | Unknown | Destroy; `PG_CANCEL_SETTLEMENT_TIMEOUT` | Authorized safety bound |
| `ROLLBACK_TIMEOUT` | Adapter rollback timer | rollback not ordinarily settled | Unknown/failed | Destroy; `PG_ROLLBACK_TIMEOUT` | Authorized |
| `CLIENT_DESTROY_TIMEOUT` | Lifecycle/harness close observation | destruction not observed | Client never reusable | Retain `PG_CLIENT_DESTROY_REQUIRED`; escalate evidence | Authorized |
| `OVERALL_OPERATION_TIMEOUT` | Outer operation/harness | terminal budget exhausted | Treat as unknown unless already terminal | Destroy if owned; bounded failure publication | Authorized |

Strict precedence is phase-based: checkout and connection establishment complete before client ownership; within a transaction `SERVER_LOCK_TIMEOUT <= SERVER_STATEMENT_TIMEOUT < APPLICATION_DEADLINE < OVERALL_OPERATION_TIMEOUT`. Settlement grace starts only after an application deadline and must fit the remaining overall budget. Rollback starts only after ordinary settlement and has a bounded budget within the overall deadline. Destroy begins immediately when mandated and has its own observation bound. Configuration MUST reject equality or inversion where strict `<` is shown. The same `connectionTimeoutMillis` option has phase-dependent pool meanings; stage tagging disambiguates it.

## 8. Query settlement

“Query settled” for reuse means all of the following: the ordinary pg query promise has resolved or rejected; the driver has consumed the command cycle through `ReadyForQuery`; a post-cycle public transaction status can be read; no client error/end/socket/protocol uncertainty was observed; no local query-timeout path or unresolved cancellation/deadline remains; and adapter ownership still matches.

A JavaScript promise alone is insufficient. A local `query_timeout` rejection is specifically not settlement. A cancellation request being sent or accepted would not be settlement. `IDLE` means transaction state, not socket health or sanitation.

Rollback MAY start only after ordinary settlement. Normal release additionally requires section 11. Destroy does not require settlement and is the required escape from uncertainty. Evidence MAY be published only after a terminal release decision; pre-terminal events are bounded in-memory inputs, not final success.

Race rules:

- Result after application deadline: ignore it for success; destroy remains mandatory.
- Server timeout versus application deadline: first observed authoritative event wins; ordinary `57014` settlement before the deadline permits rollback, otherwise destroy.
- A hypothetical late cancel after completion is unsupported and never emitted by this adapter.
- Socket close, protocol error, or client error during cancellation/settlement immediately selects destroy.
- Rollback before prior settlement is prohibited.
- Error event before query rejection selects destroy even if a rejection later arrives.
- Client error after a successful COMMIT but before release makes reuse unsafe; commit outcome may remain known, but destroy is mandatory.

## 9. Transaction-state authority

Authority is a combination of the adapter-owned state machine and documented `getTransactionStatus()` sampled only after ordinary query settlement. Map `I -> IDLE`, `T -> IN_TRANSACTION`, `E -> FAILED_TRANSACTION`, and `null`, exception, unrecognized value, or unavailable method -> `UNKNOWN`.

Adapter state is sufficient to decide that ownership exists and that an operation was attempted; it is never sufficient for normal release after an error. Wire-derived status is required after `BEGIN`, business-query failure, timeout, `COMMIT`, and `ROLLBACK`. Disagreement between local and wire state yields `UNKNOWN`. `UNKNOWN` always destroys.

Lifecycle mapping: acquired/no transaction is `IDLE`; begun/active is `IN_TRANSACTION`; ordinary in-transaction error is `FAILED_TRANSACTION`; any unsettled, disconnected, contradictory, or ambiguous condition is `UNKNOWN`.

## 10. Rollback contract

- An ordinarily settled query failure in an explicit transaction requires one rollback attempt.
- An ordinarily settled server statement/lock timeout requires one rollback attempt.
- A local deadline requires settlement proof first; because the selected policy destroys when the local deadline wins, rollback is not attempted on that client.
- Socket, connection, protocol, client-error, or unknown-status conditions skip rollback and destroy.
- A normally reported COMMIT error followed by ordinary settlement with `T` or `E` permits one rollback attempt and retains `PG_COMMIT_FAILED`.
- A COMMIT interruption, missing ordinary settlement, connection error, or contradictory status makes the commit outcome unknowable. No rollback can prove non-commit; retain `PG_COMMIT_OUTCOME_UNKNOWN` and destroy.
- ROLLBACK rejection, timeout, non-`I` status, or error event retains rollback failure/timeout and destroys.

Maximums are: explicit cancel attempts `0`; rollback attempts `1`; terminal release calls `1`. There is no automatic transaction retry in this contract. Serialization/deadlock retry policy belongs to a later explicitly bounded operation-level design.

## 11. Release/destroy contract

`NORMAL_RELEASE` invokes `client.release()` exactly once and requires every condition: ordinary query settlement; proven terminal transaction status `I`; known COMMIT/ROLLBACK outcome; no client error/end; no socket/protocol uncertainty; sanitation passed; borrower identity valid; no cancellation/deadline/query timeout outstanding; no pending query known to the adapter; and no unresolved timeout. Pool rotation may still remove the client afterward.

`DESTROY_RELEASE` invokes documented `client.release(true)` exactly once. It is mandatory for unknown transaction state, failed/timed-out rollback, unresolved cancellation/settlement, socket close, protocol failure, uncertain client error, ambiguous transaction outcome, pending protocol uncertainty, post-COMMIT reuse uncertainty, sanitation failure, borrower mismatch, or invalid release state. The call is the terminal ownership action; code MUST NOT assume it returns a promise proving socket closure.

`PG_QUERY_FAILED` excludes local timeout, server statement timeout, lock timeout, socket, protocol, client, connection, unknown-status, and cancellation/settlement failures. `PG_CANCEL_REQUEST_FAILED` remains reserved and MUST NOT be emitted by this model because explicit cancel attempts are prohibited. Fake lifecycle categories map by semantic stage: fake query failure -> `PG_QUERY_FAILED`; fake timeout/cancel -> statement timeout or settlement code; fake rollback/release/sanitation/identity failures -> the correspondingly named `PG_*` code; fake connection uncertainty -> socket/protocol/client/status code. Raw messages never select authority.

Final failure precedence is: transaction-outcome ambiguity; socket/protocol/connection/client loss; unknown transaction status or settlement; rollback failure/timeout; identity/sanitation/release-state safety failure; pool lifecycle failure; then the originating query/statement/lock failure. A later, more specific safety failure supersedes the original primary code because it determines terminal reuse safety. The bounded event history MAY retain the earlier closed code as a non-primary stage event. One scenario result has exactly one final primary failure code.

Retained error evidence is limited to closed code, allowlisted SQLSTATE, selected category (`postgres_error`, `connection`, `socket`, `protocol`, `client`, `pool`, `adapter`), stage, retryability classification, transaction-state classification, and an optional cryptographic hash of bounded raw diagnostic bytes. It MUST exclude connection strings, credentials, host/project identifiers, sensitive query text/values, stack traces, tokens, and arbitrary messages.

## 13. SQLSTATE allowlist

Only these exact values may be retained: `57014` query canceled (including statement timeout), `55P03` lock not available (including lock timeout), `40001` serialization failure, `40P01` deadlock detected, `25P02` failed SQL transaction, and connection/protocol codes `08000`, `08001`, `08003`, `08004`, `08006`, `08007`, `08P01`. Classification MUST use the code and stage, never message matching. Unknown codes are replaced by category only.

## 14. Pool/client error behavior

A pool `error` listener MUST be installed synchronously during pool construction. It sanitizes and records `PG_POOL_ERROR`; pg-pool removes the affected idle client. The handler MUST NOT throw. An idle-client error poisons that client, not automatically the entire pool; systemic escalation policy is outside this freeze.

Every checked-out client MUST have an ownership-scoped `error`/`end` observer. An event marks state unknown and mandates destruction/no reuse. After release, idle errors belong to the pool handler. Unexpected idle close is treated equivalently. Pool shutdown rejects new ownership, drains according to public `pool.end()`, and any shutdown race with a borrower selects destroy/closed failure rather than normal evidence. Missing mandatory listeners is a construction failure; process crash from an unhandled pool error is prohibited by design.

## 15. Direct/PostgreSQL pooler compatibility

Generic behavior MUST work with direct PostgreSQL and transaction poolers: one client per explicit transaction; transaction-local timeout/context establishment; unnamed statements only; no session-state persistence; no backend-PID or physical-connection affinity assumptions; rollback before eligible release; aggregate pool observations only.

Direct PostgreSQL can technically provide backend key cancellation, but this contract intentionally does not use it. PgBouncer transaction pooling assigns a server connection only for a transaction and does not preserve session features. Consequently session `SET`, `LISTEN`, session advisory locks, SQL `PREPARE`, and named protocol plans are prohibited generic dependencies. Provider mode/configuration remains deployment evidence, not inferred behavior.

## 16. Supavisor limitations

Supavisor transaction mode multiplexes client connections over backend connections and is intended for transient/serverless workloads. The adapter MUST use transaction-local settings and omit prepared-statement names. It MUST NOT treat a visible PID, connection, or client object as durable physical-backend identity and MUST NOT construct CancelRequest traffic. Provider-specific proof of timeout SQLSTATEs, rollback/status behavior, capacity, and error surfaces remains required in PD.8; this document makes no Supavisor execution claim.

## 17. Vercel/Fluid limitations

Future deployment SHOULD lazily reuse a process-global pool and MUST NOT call `pool.end()` per request. Connection budget, cold start, hot reuse, suspended-instance behavior, in-flight work at suspension, function termination, and deadline headroom remain unproved. Any Fluid helper such as idle-connection attachment requires its own package/API review before use. PD.9 must test singleton reuse, platform deadline precedence, idle cleanup, suspension/resumption, in-flight termination, pool capacity, cold/hot behavior, and sanitized evidence. Platform termination is not a cancellation acknowledgment.
