# A2.3 Pooling and Session Safety

Status: external proof required; no pool approved

## Transaction pooling

The candidate contract requires all statements—begin, identity proof, role activation, exact acquisition, result validation, commit/rollback—to remain on one backend connection for one transaction. Transaction-local role and approved GUC state must disappear on transaction end. A pooler that multiplexes statements within a transaction is incompatible.

External Supabase/Supavisor evidence must prove:

- one backend per explicit multi-statement transaction;
- support for transaction-local role activation with PostgreSQL 17.6 membership options;
- behavior of prepared statements and driver query mode;
- transaction-level advisory locks remain on the pinned backend until transaction end;
- no session advisory lock is used;
- transaction-local settings do not cross return;
- cancellation/statement timeout rolls back or produces an explicitly unknown outcome;
- backend cleanup before reuse;
- TLS, pool port, limits, queues and failover behavior.

A disconnect after send never proves rollback. The application reconciles the same idempotency tuple.

## Session pooling

Session pooling retains a physical session longer and may survive warm Vercel process reuse. Safe release requires proof after success, rollback, SQL error, cancellation, timeout and aborted request that:

- role returned to the dedicated LOGIN;
- transaction is idle and not aborted;
- search path, row security and all GUCs match baseline;
- prepared statements, portals, listeners, advisory locks and temporary objects are absent or approved;
- `RESET ALL`/`RESET ROLE` semantics are sufficient, or `DISCARD ALL` is supported and effective;
- cleanup failure destroys rather than returns the connection.

Vercel freeze/thaw, concurrent requests and process termination can interrupt JavaScript cleanup. Therefore `finally` is necessary but not sufficient. Session pooling remains rejected until destructive connection disposal and reuse-contamination testing pass.

## Activation model comparison

| Model | Identity/scope | Cleanup and risk | Decision |
|---|---|---|---|
| `SET ROLE afex_core_runtime` | Changes `current_user` until reset/session end; `session_user` remains LOGIN | High contamination burden if session-scoped | Not preferred. |
| Transaction-local Runtime activation | `current_user` changes only within explicit transaction if PostgreSQL/pool semantics are proven | Rollback/commit should restore; still verify before release | Preferred activation mechanism pending isolated proof. |
| Login directly as runtime-capable role | Conflates LOGIN and Runtime; contradicts NOLOGIN separation | No activation step but excessive standing authority | Rejected. |
| Additional SECURITY DEFINER wrapper | Adds another privileged surface and owner contract | Does not solve approved invoker identity | Rejected absent contract amendment. |
| PostgREST switching | Managed role/session behavior; service-role broad authority | No application control of backend cleanup | Rejected. |
| Separate command service | Service owns bounded pool and cleanup | Extra network/ops, but strong isolation | Conditional fallback. |

## Prepared state and timeouts

The driver must either disable named prepared statements where pool mode requires it or prove compatibility. Transaction timeout, statement timeout, lock timeout, driver timeout and HTTP timeout require ordered values so the database/driver resolves before the outer request disappears where possible. Exact numbers depend on measured A1 budgets.

On timeout, cancellation is attempted once; the connection is quarantined until transaction state and identity are proven. If proof is impossible, destroy it. The command result remains unknown and is reconciled by same-key acquisition/status behavior—never reissued with a new key.
