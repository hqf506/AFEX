# A2.1S — Runtime Privilege Closure Design

Status: DESIGN ONLY — NOT AUTHORIZED FOR EXECUTION

## Executive conclusion

The proposed dedicated LOGIN architecture remains viable, but no eligible LOGIN
exists and `afex_core_runtime` is not yet a least-privilege execution role. The
role itself has safe attributes and owns no catalog object. Its excessive
surface is overwhelmingly inherited from PUBLIC function ACLs, not direct
grants or role inheritance.

The final runtime contract is:

- `afex_core_runtime` remains NOLOGIN, NOINHERIT, NOSUPERUSER, NOCREATEDB,
  NOCREATEROLE, NOREPLICATION, and NOBYPASSRLS;
- a separately approved managed LOGIN may receive one membership permitting
  SET ROLE to `afex_core_runtime`, with no inheritance or administration;
- `afex_core_runtime` directly executes only the exact P2D.20 acquisition
  signature;
- the canonicalizer remains owner-only and is reached only transitively;
- the runtime role owns no schema, relation, sequence, or function;
- it receives no direct table, column, sequence, ledger, payload, command,
  authorization-context, or outbox access;
- unrelated PUBLIC execution must be closed per exact function signature and
  owner, never by schema-wide wildcard;
- Supabase-, storage-, realtime-, and extension-managed objects are not changed
  without separate owner/dependency evidence.

## Exact risk-flag explanation

### `rls_bypass_risk=true`

This is not caused by `afex_core_runtime` attributes: both SUPERUSER and
BYPASSRLS are false. It is not caused by runtime ownership: section 170 is
empty. It is not caused by a discovered LOGIN: candidate count is zero.

The authoritative section-260 logic also flags executable, unexpected
SECURITY DEFINER functions whose owner is superuser/BYPASSRLS or owns an RLS
table without FORCE RLS. The runtime role can execute numerous PUBLIC-derived,
postgres-owned SECURITY DEFINER legacy functions. That exact branch makes the
result true.

### `direct_object_access_unsafe=true`

The name is broader than direct ACL provenance. It is an aggregate of relation,
schema, and default-privilege findings. Evidence proves:

- PUBLIC-derived SELECT on the two `extensions.pg_stat_statements*` views;
- PUBLIC-derived `public` schema USAGE;
- PUBLIC and managed-role default ACL rows that the diagnostic conservatively
  treats as future broadening paths.

There is no direct runtime table ACL, sequence ACL, ownership path, or Core V2
ledger/outbox access in the captured evidence.

### `execute_surface_too_broad=true`

This is a real least-privilege violation, not merely the section-230 naming
heuristic. Section 100 proves 127 PUBLIC-derived executable functions beyond
the single direct P2D.20 ACL. Section 230 merely selects 31 names for attention;
it does not cause the authoritative flag. Trigger-shaped and managed functions
may be false positives as caller entrypoints, but their PUBLIC EXECUTE ACL is
still real catalog exposure.

## Final function contract

### Caller executable

Only:

`public.acquire_atomic_order_command_v1(uuid, uuid, uuid, text, text, text, text, timestamp with time zone)`

Owner: `afex_function_owner`; SECURITY DEFINER: true; fixed search path:
`pg_catalog`.

### Owner-only transitive helper

`public.canonicalize_atomic_order_json_v1(jsonb)`

This function is owned by `afex_function_owner`, has only owner EXECUTE in the
captured ACL, and must remain non-executable by `afex_core_runtime`. P2D.20 may
use it transitively under its SECURITY DEFINER owner context. It is both
`REQUIRED_TRANSITIVE_INTERNAL` and `OWNER_ONLY_HELPER`.

### All other functions

No additional runtime allowlist entry is approved. Public-schema legacy
functions require exact-signature closure analysis. Functions owned by
Supabase storage/auth/realtime or extension owners remain managed do-not-touch
until their ownership, dependency, and supported ACL model are proven.

## Schema contract

| Schema | Intended runtime contract |
|---|---|
| `public` | USAGE only as required to resolve the exact acquisition function; no CREATE. |
| `pg_catalog` | Implicit catalog resolution only; never grant CREATE or ownership. |
| `information_schema` | No explicit runtime grant. |
| `auth` | No direct grant; Supabase-managed do-not-touch. |
| `storage` | No direct grant; storage-managed do-not-touch. |
| `realtime` | No direct grant; Supabase-managed do-not-touch. |
| `extensions` | No direct grant; extension-managed do-not-touch pending disposition of PUBLIC view ACLs. |
| `graphql` / `graphql_public` | No direct grant; managed do-not-touch pending owner evidence. |
| `vault`, `net`, `cron` | No direct grant; managed/extension do-not-touch if present. |
| Future Core V2 schema | No implicit access; exact USAGE only if an approved entrypoint is located there. |

## Table and sequence contract

`afex_core_runtime` owns none and has no direct privilege on any table, view,
materialized view, foreign table, sequence, Core V2 ledger, payload, command,
authorization context, or outbox object. No table or sequence grant is approved.
All state access occurs inside the approved SECURITY DEFINER entrypoint under
the separate function owner.

## Role membership contract

- `afex_core_runtime` is not a member of any other role.
- No browser, `anon`, `authenticated`, service, worker, or issuer role becomes a
  member of it.
- A future managed application LOGIN may receive exactly one membership in
  `afex_core_runtime`: administration false, inheritance false, SET true.
- That LOGIN is NOINHERIT and cannot SET ROLE to any additional role.
- The existing `postgres` membership is preserved unless separate Supabase
  ownership and installer evidence explicitly authorizes a change.

## Login and session architecture

The application LOGIN is distinct from `afex_core_runtime`. Each transaction
must begin in the LOGIN identity, deliberately enter the runtime role, execute
only the approved operation, and restore the original role before returning the
connection. Connection return must fail closed if identity restoration cannot
be proven.

Transaction pooling is preferred only if the driver guarantees transaction
state removal. Session pooling requires explicit reset evidence covering role,
search path, row security, custom GUCs, prepared statements, and error paths.
RESET ROLE alone is insufficient if other session state survives; DISCARD ALL
may be required but must be supported and measured. Unknown pool behavior keeps
the architecture blocked.

## Non-generic safety rules

Never apply schema-wide function revocation, blanket storage-schema revocation,
unscoped default-privilege alteration, managed-object ownership transfer, or
changes to postgres/authenticator/service/service-role/Supabase memberships.
Every future action is bound to an exact signature, owner, current ACL, and
dependency proof.
