## 2. Test layers

### Unit

- exact argument order and tuple length;
- missing/extra input rejection;
- actor/session source versus requested tenant/branch;
- no role/capability input;
- canonical key/string/number/timestamp/null/array/modifier behavior;
- bytea accepted and rejected raw forms;
- each disposition/status/nullability matrix;
- deep freeze and mutation resistance;
- safe error/redaction behavior.

### Contract and golden vectors

- TypeScript and PostgreSQL canonical payload/projection byte equality;
- exact SHA-256 and canonical-size values;
- semantic-equality and included/excluded field vectors;
- P2D.20 8-input/12-output freeze;
- P2D.18A conditional-state coverage.

### Static

- one sealer and allowlisted caller;
- one bytea normalizer and result mapper caller;
- no direct P2D.20 elsewhere;
- no browser/route internal reachability;
- no client/env/database code in contracts/canonical modules;
- no direct ledger/outbox references or legacy fallback;
- root exports remain narrow.

### Fake-client integration

- zero/one/multiple rows;
- transport failure before/after simulated send;
- timeout, abort and cancellation;
- malformed fields and driver values;
- retry uses byte-identical tuple and same key;
- no real DB call.

### Future controlled evidence

- read-only role/membership/function privilege diagnostic;
- isolated driver representation evidence;
- canonical golden vectors against installed function without mutation only if an
  independently approved read-only facility exists;
- later controlled acquisition tests require separate authorization because
  P2D.20 mutates durable ledgers.

## 3. Review gates

Every subphase requires:

1. exact baseline and clean-tree precondition;
2. narrow file allowlist;
3. TypeScript, lint, contract, boundary, and build validation as applicable;
4. no secrets, package changes, route imports, feature flags, or activation;
5. independent source/security review;
6. explicit resolution or deferral of every decision-log item; and
7. no commit/push without a separately authorized controlled phase.

Any Critical/High security finding, privilege ambiguity, canonical mismatch,
second sealer, raw-row leakage, direct table access, or route activation blocks
progress.

## 4. SQL and Production gates

| Gate | Minimum evidence | Mutation allowed |
|---|---|---:|
| Managed LOGIN identity | Read-only roles/memberships/function ACL/session behavior | No |
| Driver bytea/timestamptz shape | Isolated fake first; read-only Production metadata/value evidence if available | No |
| Full authorization evidence retrieval | Catalog/source review and SQL design | No in A2.1–A2.5 |
| New evidence RPC if required | Independent SQL design/security review and separate migration authorization | Only later explicit phase |
| P2D.20 integration | Controlled non-Production/disposable environment because acquisition writes | Not in A2 design phases |

No A2.1 SQL is generated. The user must separately authorize any diagnostic or
send future SQL for review.

## 5. No-activation gates

- No `app/`, route, component, hook, Server Action, POS, or Admin edits.
- No Core V2 feature-state selection or environment flag.
- No call from current `POST /api/orders`.
- No legacy write replacement/fallback/dual write.
- No P2D.20 call in unit tests or build.
- No Production credential or configuration change.

## 6. Completion and commit gates

A2 is commit-ready only after:

- all stable scanner IDs have isolated fixtures;
- all P2D.18A vectors pass;
- driver and privilege evidence is reviewed;
- authority evidence retrieval is approved;
- the sole sealer/import graph is proven;
- failure, retry, redaction and no-activation tests pass;
- independent review reports no unresolved Critical/High issue; and
- the diff contains only approved A2 modules/tests/docs.

route-free. In parallel as a separately authorized read-only evidence task, the
