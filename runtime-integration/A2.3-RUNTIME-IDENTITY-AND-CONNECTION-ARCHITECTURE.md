## Proposed identity architecture

`afex_core_runtime` remains NOLOGIN. A separate conceptual LOGIN, named here `afex_core_app_login` only as a design label, authenticates the trusted command boundary. It owns no object and receives no direct schema, table, column, sequence, or function ACL. Its only relationship is SET-only membership in `afex_core_runtime`.

The preferred conditional topology is:

Next.js Node trusted facade → approved Supabase transaction pool endpoint → dedicated LOGIN → one explicit database transaction → transaction-local activation of `afex_core_runtime` → exact P2D.20 call → commit/rollback → identity verification → connection return.

This topology is **not approved for implementation** until Supabase/Supavisor proves transaction pinning, multi-statement support, role activation, cancellation, and cleanup semantics.

## Alternatives and rank

1. **Preferred pending evidence:** dedicated LOGIN through Supabase transaction pooling. Best expected serverless capacity if one physical backend is pinned for the entire transaction and state is removed at transaction end.
2. **Acceptable fallback pending evidence:** separately hosted trusted command service with a bounded dedicated pool. Strong isolation and observability, but adds network, deployment and operational burden.
3. **Deferred:** Vercel direct PostgreSQL connection using the dedicated LOGIN. Technically controllable, but network support, connection storms, limits, regions and lifecycle are unproven.
4. **Rejected unless a new proof reverses risk:** session pooling from Vercel. Cleanup and freeze/thaw contamination risk are too high without exhaustive reset/disposal evidence.
5. **Rejected:** service-role/PostgREST as the Core V2 caller, direct login as `afex_core_runtime`, generic SECURITY DEFINER wrappers, browser/API role switching, and any role name supplied by request input.

## Direct connection assessment

Direct connections are server-side Node only. They require TLS verification policy, network reachability, IPv4/IPv6 evidence, bounded per-instance pools, global admission control, cold-start storm protection, credential rotation, driver cancellation, failover behavior, preview isolation, and region latency measurement. A Capacitor client never connects directly. Without Vercel region and Supabase compute/connection evidence, this option cannot be capacity-approved.

## Separate command service assessment

A separate service must run near the database, authenticate AFEX requests using short-lived signed server-to-server credentials, reject replays, maintain a bounded dedicated pool, expose one idempotent command endpoint, and provide health, audit, metrics, secret rotation, failover and independent deployment controls. Its security advantage is connection ownership and reduced Next.js secret exposure. It is justified only if managed transaction pooling cannot prove role and cleanup invariants.

## A1/A2.2 reconciliation

The conditional decision preserves Authorization Context, idempotency, replay, payload, response, error, performance and security contracts. It remains disabled by default; never dual-writes; and never falls back to legacy after a send, acceptance, timeout or unknown outcome. No conflict was found. Missing numeric performance and topology evidence remains blocking rather than silently changing A1.
