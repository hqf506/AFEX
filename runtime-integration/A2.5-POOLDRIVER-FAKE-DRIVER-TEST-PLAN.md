## 6. Fake pool model

`FakePool` has a closed maximum, deterministic client identifiers, and a real deterministic FIFO waiter queue. A full checkout returns a waiter handle; normal release assigns the returned client to exactly the oldest waiter, destruction creates capacity for exactly the oldest waiter, and explicit waiter cancellation removes that waiter. Exact checked-out/idle/total/destroyed/released/queued counts and permanent exclusion of destroyed clients are asserted at each queue boundary.

Each pool owns an independent monotonic waiter sequence. Waiter IDs are immutable, creation-ordered values from `FAKE_WAITER_0001` through `FAKE_WAITER_9999`; cancellation, resolution, consumption, release, destruction, and client reuse never reset or reuse an ID. Invalid sequence starts fail with `WAITER_ID_SEQUENCE_INVALID`, and creation after `FAKE_WAITER_9999` fails closed with `WAITER_ID_SEQUENCE_EXHAUSTED`. IDs are fake-only evidence: they do not represent node-postgres or provider waiter identity.

## 7. Fake client model

`FakeClient` holds a lifecycle state, symbolic identity, positive fake backend PID, transaction status, contamination flags, sanitation result, safe symbolic operation log, and closed fault set. It rejects double release and use after release or destruction.

## 8. Lifecycle state machine

The pure reducer accepts only the frozen state and event vocabularies. Invalid transitions fail closed. `RELEASED` and `DESTROYED` are terminal and cannot be resurrected.

## 9. Timeout hierarchy

The required strict ordering is `database_timeout_ms < client_timeout_ms < process_timeout_ms`. Missing, zero, negative, non-integer, equal, reversed, or oversized values fail with `TIMEOUT_CONFIGURATION_INVALID`.

## 10. Cancellation model

Cancellation is simulated deterministically. Normal release requires settled cancellation, proven rollback, and passing sanitation. Failed or dirty cancellation requires destruction.

## 11. Release versus destroy policy

Normal release is possible only from committed, rolled-back, or cancellation-rollback-proven state after sanitation. Unknown socket, protocol, identity, sanitation, rollback, cancellation, and unresolved-timeout states require destruction.

## 12. Identity and sanitation policy

Identity labels are nonsecret symbolic values. Missing or mismatched identity fails closed. Only `sanitize()` may clear contamination and emit `SANITATION_PASS`; public event application cannot emit that event. Pool return never clears borrower context. Contamination or sanitation failure prevents normal release and requires destruction.

## 13. Fixture catalog 001–036

The immutable catalog `A25-PD3-FX-001` through `A25-PD3-FX-036` covers commit, rollback, query failure, commit failure, timeouts, cancellation, socket/protocol failure, identity, sanitation, invalid release, terminal-state misuse, pool ordering/reuse, destroyed-client exclusion, borrower isolation, invalid configuration, unknown state/event/fault, invalid identity/PID, mutable-input defense, and replay equality. The primary pass dispatches every fixture exactly once, executes its behavior, and compares terminal state, action, failure code, and every pool counter with its frozen expectation.

## 13.1 Honest count methodology

Behavior cases are registered under unique names. Category counts are derived from the sizes of those unique-name registries, fixture count increments only when a fixture is dispatched, and duplicate registration fails. Metadata checks and raw assertion totals do not substitute for behavioral case counts. Padding loops, unconditional assertions, and repeated cases added solely to reach a threshold are prohibited.

## 14. Deterministic scheduling

`FakeClock` advances only by caller-supplied integer milliseconds. Equal deadlines execute by creation order; cancellation is explicit; no real sleep or wall clock participates in authority.

## 15. Immutability contract

Reducer inputs are not mutated. Returned lifecycle values and all nested fixture values are frozen.

## 16. Canonical hashing

Objects are recursively key-sorted, serialized as canonical JSON, and hashed with SHA-256. No timestamp is generated by the reducer.

## 17. Failure-code contract

Unknown state/event, invalid transition, invalid release, timeout configuration, terminal resurrection, identity, sanitation, rollback, cancellation, socket, and protocol failures have deterministic closed codes.

## 18. Success marker

Full success emits exactly one `A25PD3_900_FAKE_DRIVER_LIFECYCLE_TESTS_PASS` marker. Failure emits one marker beginning `A25PD3_FAILURE_` and exits nonzero.

## 19. No-network/no-database proof

Executable modules use Node built-ins only for cryptographic hashing and read-only semantic contract loading. They import no network, child-process, database, package-manager, environment, or socket API. Operations are symbolic identifiers rather than executable statements.

The Node suite does not claim to read Git objects. It verifies an immutable, compiled-in authority manifest containing all four approved contract blob hashes and performs semantic reads of the matrix and schema. A separate no-network review step is authoritative for hashing exact `HEAD:<path>` and `:<path>` bytes, proving HEAD/index equality, and matching those hashes to the manifest. Physical tracked worktree bytes are never the hash authority.

## 20. Limitations of fake evidence

Fake Driver evidence proves application lifecycle logic only. It does not prove node-postgres, Supavisor, PostgreSQL, Vercel, network, TLS, provider cancellation, or physical backend sanitation behavior.
