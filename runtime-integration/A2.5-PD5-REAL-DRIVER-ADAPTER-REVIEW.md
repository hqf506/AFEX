## Correction R1 review record

- External release is invoked once only after irreversible terminalization. Normal-release exceptions map to `PG_RELEASE_STATE_INVALID`; destroy-release exceptions map to `PG_CLIENT_DESTROY_REQUIRED`. Neither path restores ownership or retries.
- COMMIT has one-attempt pending state and deterministic application/overall deadline ownership. Deadline-first outcome is permanently ambiguous; late resolution or rejection is consumed without state restoration, rollback, or retry.
- One centralized gate excludes overlapping query, COMMIT, rollback, sanitation, and release operations. Overlap is a lifecycle-state violation mapped to `PG_RELEASE_STATE_INVALID`.
- Borrowers cannot submit arbitrary text. They submit a closed operation descriptor; only the injected, separately reviewed executor can construct a future pg query. Raw text, names, mutation flags, and unknown fields are rejected.
- Throwing transaction-status observation becomes `UNKNOWN` and forces destructive disposition without retaining the thrown message.
- After normal release the retired lease listener is detached; later client-error authority belongs to the pool/client owner. Such an event cannot resurrect or mutate the retired lease.
- Checkout rejection carrying the frozen `PG_POOL_SHUTDOWN` classification is tested directly; provider shutdown behavior remains future evidence.
- Added negative coverage includes both release exception modes, throwing status, COMMIT success/deadline/overall/late settlement, all required operation overlaps, duplicate COMMIT, normal post-release error, and trusted descriptor isolation.

## Correction R3 rollback-status preservation

Rollback command outcome and post-command transaction observation are separate internal dimensions. `PG_ROLLBACK_FAILED` is reserved for command rejection or a successfully returned rollback that ends in the frozen non-idle `T`/`E` states. A successful command whose status is missing, invalid, or throwing maps to `PG_TRANSACTION_STATUS_UNKNOWN`. Timeout remains `PG_ROLLBACK_TIMEOUT`. Only successful command plus fresh `IDLE` may proceed to sanitation.

Direct tests added:

- `59 rollback succeeds with missing status method then destroys`
- `60 rollback succeeds with invalid status then destroys`
- `61 rollback succeeds with throwing status then destroys`
- `62 rollback succeeds with idle status and may release normally`
- `63 rollback succeeds but remains in transaction and destroys`
- `64 rollback succeeds but remains failed transaction and destroys`
- `65 statement timeout then rollback unknown status precedence`

Existing tests 21 and 54 directly retain timeout and command-rejection mappings. The compound reruns establish `PG_ROLLBACK_FAILED` for query failure followed by command rejection, `PG_TRANSACTION_STATUS_UNKNOWN` for query or statement-timeout origins followed by successful rollback with unknown status, and `PG_ROLLBACK_TIMEOUT` for timeout. Attempts remain exactly once and every failure is non-retryable.
