# A2.4B.2 SECURITY DEFINER Safety Contract

Status: MANDATORY PRECONDITION FOR DIRECT EXECUTE

## Entrypoint identity

The only approved application entrypoint is the exact P2D.20 signature. Its owner must be the reviewed function owner and must never be the application LOGIN. Owner attributes, owned objects, memberships, SETtable roles, and privilege reachability require fail-closed attestation.

## Definition safety

The entrypoint must retain:

- SECURITY DEFINER with no caller-controlled execution identity.
- A fixed empty or explicitly safe search path, consistent with the installed reviewed definition.
- Fully schema-qualified references for every non-catalog object.
- No unsafe dynamic SQL, caller-supplied identifier, role target, schema target, function target, search path, or authority GUC.
- Exact immutable/canonical request validation and database-derived fingerprint behavior.
- Authorization-context validation and trusted actor, tenant, and branch scope verification.
- Exact idempotency, acquisition disposition, advisory-lock, atomicity, and no-orphan contracts.
- Exact typed input and output signature with fail-closed handling of unknown values.

## ACL closure

- Grant the dedicated LOGIN EXECUTE only on the exact signature.
- Close PUBLIC, `anon`, `authenticated`, and every unapproved direct/effective caller path.
- Explicitly review `service_role`; it remains rejected as the application identity and receives no new grant under this amendment.
- Prevent default EXECUTE leakage for this function and future functions.
- Preserve owner-only access to internal helpers.
- Grant no table, column, sequence, ownership, schema CREATE, or generic function privilege to the LOGIN.

## RLS and object boundary

RLS and FORCE RLS remain enabled where frozen. SECURITY DEFINER behavior is accepted only with the reviewed owner and function body; it is not a reason to weaken RLS, policies, ownership, or table ACLs. The caller cannot select, mutate, or enumerate underlying objects outside the entrypoint.

## Operational safety

- Postcondition attestation must prove owner, signature, function source/hash contract, SECURITY DEFINER, search path, dependencies, grants, effective denials, and absence of overload leakage.
- Forward installation and rollback/revocation must be separately reviewed and fail closed.
- Emergency procedures disable the LOGIN and revoke the exact signature grant.
- No dual write or shadow mutation is permitted.
- After a Core V2 request is sent or may have been accepted, there is no fallback to legacy order creation. Unknown outcomes reconcile with the same idempotency tuple.

Any owner, definition, dependency, ACL, RLS, policy, identity, canonicalization, or scope mismatch blocks activation.
