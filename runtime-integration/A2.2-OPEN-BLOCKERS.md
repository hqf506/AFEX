# A2.2 Open Blockers

Status: implementation and activation blocked

## Critical blockers

| Blocker | Required evidence / decision | Blocks |
|---|---|---|
| Dedicated application LOGIN absent | Name, attributes, owner, creator, credential custody, rotation, revocation, connection limit | All trusted connection implementation. |
| Membership unapproved | Exact SET-only, no-inherit, no-admin relationship to `afex_core_runtime`; do-not-touch postgres relationship preserved | Role activation. |
| Pool mode unknown | Direct, transaction, or session pool selection and provider-supported semantics | Connection ADR. |
| Session cleanup unproven | Success/error/timeout/cancel/abort/process-death contamination tests; role/GUC/prepared-state cleanup | Connection reuse. |
| Secret delivery undefined | Separate secret name, Vercel scope, rotation, audit, no client exposure | Deployment. |
| Vercel direct DB policy unknown | Network reachability, TLS, IPv4/IPv6, serverless suitability | Direct option. |
| Production connection limits unknown | LOGIN/pool limits, maximum concurrency, reserved capacity, backpressure | Capacity/safety. |
| Supabase-supported architecture unconfirmed | Official support for selected role activation and pool behavior | Production approval. |
| Role activation attestation absent | Runtime proof of login/session/current role and cleanup under every outcome | Any P2D.20 runtime call. |
| PUBLIC privilege closure unresolved | Exact A2.1T consumer/managed/default ACL evidence and reviewed closure | Least-privilege runtime readiness. |

## Contract blockers

- A1 contracts must be revalidated against the proposed facade before code.
- No reviewed database status/replay entrypoint currently supports the proposed `replayAtomicOrderCommand` method.
- Numeric timeout/performance budgets cannot be selected without A1 reconciliation and measured connection architecture.
- Customer-create coupling and eventual execution/outbox ownership require later Executor design; acquisition alone must not mutate customer/order data.
- Route response mapping for `in_progress`, unknown outcome, and replay requires product approval without changing A1 silently.

## Current-code risks to isolate during migration

- Service-role order route is broad and generic.
- Legacy RPC is followed by non-atomic payment, attribution, inventory, and audit writes.
- POS employee and branch originate as browser hints before server revalidation.
- Optional Core V2 idempotency reads coexist with legacy resolution.
- Offline replay and duplicate-submit paths must converge on exactly one key.
- Receipt cancellation and status changes remain separate legacy mutation concerns; they are not silently included in A2.2 acquisition.

## Explicit non-solutions

- Calling P2D.20 with `service_role`.
- Giving `anon`, `authenticated`, browser, worker, issuer, or service role membership in Runtime.
- Connecting as the NOLOGIN runtime role.
- Exposing generic `rpc`, `from`, raw SQL, driver, or connection methods.
- Assuming request-local SDK construction gives a dedicated database session.
- Assuming `RESET ROLE`, `DISCARD ALL`, or pool sanitation without evidence.
- Generating a replacement idempotency key after timeout.
- Dual writes, shadow mutations, or automatic legacy fallback.

## Readiness

A2.2A/B documentation is ready for review. A2.2C/F require external technical evidence. A2.2G and every later implementation/enablement phase remain blocked. Current Production behavior remains unchanged.
