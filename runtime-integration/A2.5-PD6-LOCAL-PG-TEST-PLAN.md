## PD.6C trusted-interface amendment

Runner preflight proved that the original closed operation map could not verify server version, the fixed lock baseline, denial-object absence, or the exact type seed without ad hoc SQL. The narrow amendment adds only `READ_SERVER_VERSION`, `READ_LOCK_TARGET`, `VERIFY_PUBLIC_DENIAL_OBJECT_ABSENT`, and `VERIFY_EVIDENCE_DENIAL_OBJECT_ABSENT`. All are fixed, parameter-free operations. Server version is reduced in SQL to a bounded numeric major/minor or major/minor/patch value and then validated. Lock verification reads only fixture row 1. The two catalog checks name only their fixed denial probes and must return boolean absence; presence fails closed.

The trusted operation vocabulary contains exactly 18 unique IDs: 14 original IDs and four new IDs. Thirteen original operations remain semantically unchanged. `READ_TYPE_FIXTURE` is the one original operation with a reviewed additive return-shape extension; it retains its original ID and decoded columns and adds only `timestamptz_logical_value` and `timestamp_logical_value`. It is not counted as a new operation. No borrower parameter, arbitrary SQL, dynamic identifier, mutation behavior, result-schema field, hidden alias, generic operation, or raw-query operation was added. No original operation was removed or renamed, and there is no unexpected operation ID.

The complete 18-ID authority is:

| Classification | Trusted operation IDs |
|---|---|
| Original, semantically unchanged (13) | `READ_STATUS_FIXTURE`, `UPDATE_STATUS_FIXTURE`, `READ_TRANSACTION_FIXTURE`, `UPDATE_TRANSACTION_FIXTURE`, `LOCK_TARGET_UPDATE`, `SAFE_DELAY`, `SET_LOCAL_STATEMENT_TIMEOUT`, `SET_LOCAL_LOCK_TIMEOUT`, `ORDINARY_QUERY_ERROR`, `DENY_PUBLIC_CREATE`, `DENY_EVIDENCE_CREATE`, `DENY_TYPE_INSERT`, `DENY_TRANSACTION_DELETE` |
| Original, additively extended (1) | `READ_TYPE_FIXTURE` |
| New (4) | `READ_SERVER_VERSION`, `READ_LOCK_TARGET`, `VERIFY_PUBLIC_DENIAL_OBJECT_ABSENT`, `VERIFY_EVIDENCE_DENIAL_OBJECT_ABSENT` |

The two added `READ_TYPE_FIXTURE` projections are database-baseline authority: they preserve the exact `678901` microseconds as fixed logical text. They are separate from JavaScript decoding observation. PostgreSQL timestamp and timestamptz values may be decoded through `Date`, whose millisecond precision cannot preserve those microseconds; the projections are not described or retained as JavaScript `Date` output, and decoding loss is not normalized away.

`TYPE_FIXTURE_BASELINE` freezes the exact logical seed. int8 and numeric compare as exact decimal representations; JSON and JSONB compare by deep logical content; bytea compares exact bytes; text arrays compare in order; and null remains exact. The type read retains the original decoded columns for observational evidence and adds separate deterministic logical projections for the timestamptz UTC instant and timestamp-without-timezone database value. These projections validate seed authority without rewriting or normalizing the actual JavaScript decoding observation and without claiming UTC semantics for the timezone-free value.

The runner has not been implemented by this amendment. No real PostgreSQL operation is authorized or claimed until this interface amendment passes independent review and the subsequent runner implementation is separately reviewed.

## Canonical Digest Version Policy

`driver_version` and `postgres_version` are retained canonical fields and participate in the canonical evidence digest exactly as represented in each bounded result. `driver_version` must reflect the exact pinned driver authority, `pg@8.22.0`. Before real PostgreSQL observation, `postgres_version` may be null only where the schema permits and the scenario has not yet executed. During executed PD.6C Direct PostgreSQL evidence, `postgres_version` must contain the observed bounded PostgreSQL version value required by the result contract.

Version values are not normalized away from digest authority. A driver or PostgreSQL version change is expected and intended to change the digest; cross-version digest equality is not claimed. Wall-clock timestamps, elapsed durations, passwords, URLs, raw errors, backend PIDs, random identifiers, and transient JavaScript object identity remain excluded from canonical digest authority.

The only direct endpoint is `127.0.0.1:55432`, classified `DIRECT_POSTGRESQL`. Port 6543 is also direct PostgreSQL and supplies no pooler evidence. The harness requires explicit operator-local configuration for database `afex_a25_pd6` and runner `afex_a25_pd6_runner`; it never reads ambient `PG*` variables or a database URL. Pool maximum is one.

## Frozen timing

| Control | Value |
|---|---:|
| lock timeout | 1000 ms |
| statement timeout | 2000 ms |
| application deadline | 3500 ms |
| settlement budget | 1500 ms |
| rollback budget | 1500 ms |
| overall operation | 9000 ms |

The overall timer begins immediately before the first borrower operation after checkout. The application timer begins immediately before the bounded query or COMMIT settlement race. Settlement begins only after the application deadline wins; rollback begins only after ordinary error settlement or settlement-budget completion. The worst sequential application-deadline path is 3500 + 1500 + 1500 = 6500 ms, leaving 2500 ms inside the 9000 ms overall boundary. Checkout/connection time is separately bounded before the operation timer. The hierarchy preserves `lock_timeout <= statement_timeout < application deadline < overall operation`, and no sub-100 ms race is used.

The separate lock-control lifecycle freezes these budgets: connect 3000 ms, `BEGIN` 750 ms, lock acquisition 1000 ms, callback critical section 1500 ms, rollback cleanup 750 ms, `end()` 750 ms, and total control operation 8500 ms. The sequential stage maximum is 7750 ms, leaving 750 ms of orchestration margin. Each stage owns only its named budget. A callback deadline terminalizes callback authority and enters cleanup without waiting for callback settlement; rollback is attempted at most once after a begun transaction, and `end()` is attempted at most once. Rejected or non-settling rollback and close operations are themselves bounded. Late callback resolution or rejection cannot restore success or repeat cleanup. Tests use an injected deterministic scheduler and fake `pg.Client`; no wall-clock sleep, private cancellation API, network connection, SQL execution, or automatic retry is used.

## PD.6C procedure

1. Confirm PD.6B review approval and clean fixture attestation.
2. Inject the password through an operator-local, ignored mechanism; do not paste it into chat or command output.
3. Construct the harness with the exact host, port, database, and runner identity.
4. Execute scenarios in numeric order, resetting mutable seeded rows only through authorized `UPDATE` operations and explicit transactions.
5. Use a separately labelled runner control connection only for the lock scenario; it is not borrower-pool evidence.
6. Capture only closed result-schema fields, canonicalize by scenario ID, and compute the deterministic digest without wall-clock values.
7. Close the adapter pool and control connection in `finally` paths. Fail closed on any uncertain settlement.
