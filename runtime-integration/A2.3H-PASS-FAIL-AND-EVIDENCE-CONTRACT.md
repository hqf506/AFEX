# A2.3H Pass/Fail and Evidence Contract

## Universal contract

Each test record must contain prerequisites, reviewed setup hash, bounded action, exact expected result, enumerated failure result, evidence paths/hashes, cleanup result, gate mapping, provider-answer classification, and reviewer decision. A test passes only when the expected result and cleanup both pass. Missing, ambiguous, conflicting, or incomplete evidence is failure for gate closure.

## Identity and contamination proof

For every applicable checkout and transaction, capture safely:

- Exact approved test `session_user`.
- `current_user` before activation, during activation, after transaction, and after reacquisition.
- Backend PID and pseudonymous client/connection identifier.
- Transaction identifier where technically available without mutation.
- Role reset, GUC reset, and `search_path` reset compared with the frozen baseline.
- Transaction advisory-lock acquisition and release.
- Absence of inherited role, arbitrary target role, previous correlation marker, prepared state, or prior client state.
- Boolean confirmation that no secret or business data appeared in evidence.

The harness must use a compiled/fixed allowlist for target roles and operations; operators cannot supply arbitrary role names or SQL.

## Per-test decision rules

| Tests | Pass condition | Failure condition | Provider confirmation sufficient? |
|---|---|---|---|
| T01 | One backend for complete explicit transaction | PID changes or transaction breaks | No |
| T02–T03 | Correct identity transition and complete reset | Wrong, persistent, inherited, or broadened role | No |
| T04–T06 | Rollback and sanitation proven after every failure mode | Residue, uncertain reusable state, or cleanup failure | No |
| T07–T08 | Zero contamination across all sequential/concurrent cases | Any state crosses clients | No |
| T09 | Correct exclusion and transaction-end release | Broken exclusion or surviving lock | No |
| T10 | Selected preparation mode is supported and isolated | Collision, unsupported hidden reuse, or residue | No |
| T11 | Same synthetic key reconciles one outcome | Duplicate, replacement key, or unsafe ambiguity | No |
| T12 | Bounded backpressure within approved limits | Storm, starvation, leakage, or unbounded wait | No |
| T13 | New credential works and revoked old fails | Old remains valid or unsafe exposure/fallback | No |
| T14 | Revoked membership prevents activation | Activation remains possible | No |
| T15 | Required verified TLS succeeds and insecure mode fails | Insecure acceptance or required verification failure | No |

## Safe evidence fields

Allowed: test/run/case IDs, approved test role names, backend PID, timestamps, boolean results, SQLSTATE, duration, pool counters, provider mode/version labels, and hashes.

Prohibited: passwords, connection strings, credentials, tokens, certificates, private hostnames, customer/tenant/order/payment data, payloads, Production idempotency keys, Production role secrets, raw environment values, and stack traces containing any prohibited value.

## Evidence disposition

Write stdout, stderr, structured result, manifest, and cleanup attestation separately. Redact before review, hash after capture, retain failures, and never commit raw evidence without a separate sensitivity review. Provider confirmation is prerequisite context; Runtime proof is mandatory for T01–T15.
