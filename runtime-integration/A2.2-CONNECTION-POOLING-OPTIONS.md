# A2.2 Connection and Pooling Options

Status: decision deferred; external evidence required

## Required session invariant

Before checkout, during work, after commit/rollback, after cancellation, and before connection return, the effective role and all relevant session state must be known. A request-local JavaScript client object does not prove a request-local PostgreSQL session.

If role activation is eventually approved, the minimum lifecycle is: acquire connection; begin transaction; verify session/login identity; activate only the approved runtime role using the approved mechanism; call only the exact acquisition entrypoint; commit or roll back; prove role/search-path/GUC restoration; then release. Any failure to prove cleanup destroys/quarantines the connection rather than returning it.

`SET LOCAL` does not change role. Transaction-scoped `SET ROLE` semantics, membership options, and driver/pool behavior require isolated proof. `RESET ROLE` alone may leave other state; `DISCARD ALL` cannot be assumed supported or automatically invoked.

| C. Supabase session pooler | Session affinity can support role state but increases contamination risk if reset is incomplete. | Higher connection occupancy; poor fit for unbounded serverless concurrency without strict caps. | Must prove success/error/timeout/abort cleanup, `RESET ROLE`, other GUC cleanup, prepared statements, and return hooks. | **Not approvable:** highest shared-session risk. |

## Why service-role RPC is not equivalent

With PostgREST/service-role, `session_user` and initial `current_user` reflect the managed API path, not the approved dedicated LOGIN/runtime transition. P2D.20 is SECURITY DEFINER, so its body executes with `afex_function_owner`, but permission to enter it is still evaluated against the invoker. Granting/calling it from `service_role` would broaden the approved invoker contract. Service role also bypasses RLS broadly and exposes generic APIs. Therefore a successful service-role RPC does not prove the `afex_core_runtime` least-privilege, membership, pool sanitation, or request-isolation model.

## External proof plan

Required evidence before selection:

1. Approved dedicated LOGIN attributes, owner, credential custody, rotation, and revocation.
2. Exact membership: administration false, inheritance false, SET true only to `afex_core_runtime`.
3. Supabase-supported direct/pool architecture and network policy.
4. Pool mode, reset hook, transaction pinning, connection return, and abort behavior.
5. Vercel runtime compatibility, maximum concurrency, connection limits, cold-start behavior, and Saudi-to-database latency.
6. Isolated tests for success, SQL error, timeout, cancellation, process termination, concurrent requests, and reused connection contamination.
7. Attestation showing exact invoker/current/session identities and zero residual role state.

Until all seven pass, no final architecture is selected and implementation beyond documentation remains blocked.
