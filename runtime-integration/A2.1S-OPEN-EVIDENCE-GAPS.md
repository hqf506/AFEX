# A2.1S — Open Evidence Gaps

Status: BLOCKING EVIDENCE REGISTER

## Critical blockers

### Managed application LOGIN

No eligible LOGIN exists. Required evidence includes final role name, creator,
owner/administrator, attributes, connection limit, validity, configuration,
exact membership options, credential custody, rotation, revocation, and proof it
cannot SET ROLE beyond `afex_core_runtime`.

### Pool and session reset

The driver and pool are unknown. Required evidence includes provider, pool mode,
transaction/session pooling, reset hook, behavior after success/error/timeout,
RESET ROLE, DISCARD ALL, prepared statements, custom GUCs, connection reuse,
and contamination tests. Until proven, A2.5 is blocked.

### Exact PUBLIC consumer inventory

The evidence proves PUBLIC ACL provenance but not every current consumer.
Repository, API, browser, scheduled-job, Supabase Edge Function, webhook, and
external integration callers must be mapped by exact function signature before
any closure action.

### Managed-object authority

Storage, Auth, Realtime, GraphQL, extension, Vault, Net, and Cron objects require
official ownership and supported-ACL evidence. No current evidence authorizes
changing them.

## High-priority gaps

### RLS amplification dependencies

The diagnostic proves executable postgres-owned SECURITY DEFINER functions but
does not enumerate every table each function reaches or every FORCE RLS state
along those paths. Function-source and dependency evidence is required per
signature.

### Trigger-only proof

Functions classified as trigger-shaped require exact trigger OIDs, tables,
events, enablement, direct callers, and function dependencies. A trigger binding
does not by itself justify PUBLIC EXECUTE.

### Helper-only proof

Helpers require caller graphs proving no direct browser, service, API, job, or
external dependency. Names are not proof.

### Default ACL causality

Section 190 contains 300 rows across managed owners and schemas. Required
evidence is a normalized tuple inventory of owner, schema, object type, grantee,
grantor, privilege, grantability, and whether future objects could become
reachable by the application LOGIN or runtime role.

### Extension views

`extensions.pg_stat_statements` and
`extensions.pg_stat_statements_info` expose PUBLIC-derived SELECT ACLs, while
runtime has no extensions-schema USAGE. Required evidence must determine
whether the ACLs are extension-managed, whether they are usable through another
path, and whether exact revocation is supported and upgrade-stable.

## Medium-priority gaps

- Whether role-level `search_path=pg_catalog, public` should remain or be reduced
  after validating all approved entrypoints' fixed function-level paths.
- Whether unlimited runtime connection limit should be normalized; this depends
  on the separate LOGIN/pool architecture and is not itself execution authority.
- Whether the existing postgres membership in runtime is required by Supabase
  installation/administration workflows.
- Exact function source hashes and dependency hashes for every proposed closure
  candidate.
- Exact ACL before-images and rollback authorization.
- Performance impact of catalog closure and connection-role transitions.

## Classification gaps

The following remain conservative until evidence exists:

- Managed-schema functions: `SUPABASE_MANAGED_DO_NOT_TOUCH`,
  `STORAGE_MANAGED_DO_NOT_TOUCH`, or `EXTENSION_MANAGED_DO_NOT_TOUCH`.
- PUBLIC legacy functions: exact categories in the matrix are design hypotheses
  requiring caller/trigger/dependency proof before mutation.
- Default ACL rows: `UNKNOWN_REQUIRES_ADDITIONAL_EVIDENCE`.
- Pool compatibility: unresolved.

## Evidence required before closure SQL approval

1. A complete exact-signature ACL manifest with source provenance.
2. Complete function caller, trigger, policy, and dependency graphs.
3. Exact owner and managed-product classification for every object.
4. Exact table/column/sequence/schema privilege inventory before and after SET.
5. Exact default ACL tuple inventory and future reachability analysis.
6. Approved managed LOGIN and membership contract.
7. Isolated pool contamination test evidence.
8. Exact change manifest, before-images, rollback manifest, and artifact hashes.
9. Security, database-owner, application-owner, and release approvals.

## Evidence required after eventual closure

The postcondition attestation defined in the migration plan must pass in full.
Any unknown, missing row, changed owner, unexpected ACL, pool failure, or legacy
regression blocks runtime integration and requires a separately reviewed
forward fix.
