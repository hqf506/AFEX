# A2.3H Supabase Support Request

## Subject

Transaction Pooler support for isolated PostgreSQL LOGIN, role activation, cleanup, and Vercel Node clients

## Message

We are evaluating a dedicated application LOGIN through the Supabase Transaction Pooler on port 6543. The LOGIN would be `NOINHERIT` and would receive SET-only membership in a custom `NOLOGIN` execution role. No browser or PostgREST caller would use this path.

Please answer for the applicable hosted Supabase service and current PostgreSQL/pooler versions:

1. Are custom LOGIN roles supported for application Runtime use?
2. Can a `NOINHERIT` LOGIN receive SET-only membership in a custom `NOLOGIN` role with SET=true, INHERIT=false, ADMIN=false?
3. In Transaction Pooler mode on port 6543, does an explicit `BEGIN` through `COMMIT` remain pinned to one PostgreSQL backend?
4. Is `SET ROLE` supported inside that explicit transaction?
5. Is `SET LOCAL ROLE` supported, and does it reset automatically at transaction end?
6. Do `COMMIT` and `ROLLBACK` clear role state before backend reuse?
7. What cleanup occurs after statement cancellation?
8. What cleanup and rollback occur after abrupt client disconnect?
9. Is backend sanitation guaranteed before reassignment to another client?
10. Are transaction-level advisory locks supported with PostgreSQL transaction semantics?
11. Are session-level advisory locks unsupported or unsafe in transaction-pool mode?
12. Are prepared statements supported, restricted, or required to be disabled for this mode?
13. Can `session_user` and `current_user` be relied upon throughout the pinned transaction?
14. Is node-postgres (`pg`) recommended from Vercel Node functions through the Transaction Pooler?
15. With database pool size 15, what application pool-size and total-connection guidance applies?
16. Which TLS mode and certificate/hostname verification behavior are required?
17. Does IPv6-only Transaction Pooler connectivity work reliably from Vercel Node functions?
18. Is the IPv4 add-on required or recommended for Vercel?

Please distinguish guaranteed behavior, documented restrictions, and behavior that must be runtime-tested. No credentials, connection strings, project secrets, or business data accompany this request.
