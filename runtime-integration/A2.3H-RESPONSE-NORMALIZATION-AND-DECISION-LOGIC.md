# A2.3H Response Normalization and Decision Logic

## Normalization

For every provider answer record evidence ID, provider, case/question ID, product/plan/version scope, captured UTC, exact redacted answer, source type, classification, confidence, G1–G12 mapping, contradictions, reviewer, and artifact hash.

Allowed answer classifications:

- `CONFIRMED_SUPPORTED`
- `CONFIRMED_UNSUPPORTED`
- `DOCUMENTATION_ONLY`
- `AMBIGUOUS`
- `REQUIRES_RUNTIME_TEST`
- `CONFLICTING`

Do not merge distinct questions into one conclusion. Preserve conditions and version/plan qualifiers. Documentation-only and ambiguous answers cannot close a gate that requires provider confirmation or Runtime proof.

## Decision logic

| Condition | Decision |
|---|---|
| Provider confirms all required semantics | Proceed to reviewed isolated Runtime-test SQL/harness design; do not approve architecture yet |
| Provider rejects any critical custom role, pinning, activation, cleanup, TLS/network, or advisory-lock semantic | Reject transaction-pool candidate and evaluate separately hosted command service |
| Provider answer is ambiguous or explicitly requires testing | Keep gate blocked and require isolated Runtime test |
| Provider cannot confirm custom LOGIN/SET-only model | Separate command service becomes preferred fallback candidate |
| Authoritative provider sources conflict | Stop; classify `CONFLICTING`; obtain reconciliation before testing |
| All mandatory Runtime tests and cleanup pass | Architecture may advance to final approval, SQL design/execution review, ADR, and disabled implementation sequencing |
| Any mandatory Runtime test fails or is indeterminate | Keep architecture blocked; remediate only without weakening contracts or evaluate fallback |

## Gate transition rules

- G1–G2 require scoped provider confirmation and later installed-state attestation.
- G3–G5, G10, and G11 require Runtime proof even when provider answers are positive.
- G6–G9 and G12 require completion of their network, capacity, lifecycle, and observability evidence.
- No single support response auto-approves the architecture.

## Decision record

The final record must cite every normalized evidence ID, list each gate state, document dissent/conflict, name the approving organizational roles, and select only an already approved architecture outcome. It must never contain secrets or raw provider credentials.
