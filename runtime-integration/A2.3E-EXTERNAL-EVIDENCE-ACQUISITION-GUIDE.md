# A2.3E External Evidence Acquisition Guide

Status: DRAFT — EXTERNAL EVIDENCE REQUIRED

## Purpose

This package collects non-secret facts needed to review the conditional A2.3 runtime topology. It does not approve an architecture, contact a provider, test a runtime, or authorize deployment.

## Fixed boundary

- `afex_core_runtime` remains `NOLOGIN` and `NOINHERIT`.
- The preferred candidate is a separate LOGIN with SET-only membership through transaction pooling.
- A separately hosted trusted command service is the fallback.
- Direct PostgreSQL from Vercel remains deferred.
- `service_role`/PostgREST and unproven session pooling remain rejected.

## Evidence classes

| Class | Meaning |
|---|---|
| DASHBOARD_VISIBLE | Directly transcribed from a narrowly scoped provider screen. |
| DOCUMENTATION_REQUIRED | Requires current official provider documentation. |
| SUPPORT_CONFIRMATION_REQUIRED | Requires a provider response tied to the applicable product and plan. |
| RUNTIME_TEST_REQUIRED | Requires a future isolated, approved runtime test. |
| UNKNOWN | No reliable evidence exists yet. |

Provider statements and dashboard values are not runtime proof. Runtime evidence must not be inferred from documentation.

## Acquisition sequence

1. Assign an evidence ID and record provider, environment, UTC capture time, and collector.
2. Collect the narrow dashboard fields in the Supabase and Vercel checklists.
3. Apply the masking rules before capture and again before review.
4. Transcribe safe values into the supplied templates.
5. Obtain current official documentation or support answers for non-dashboard facts.
6. Normalize each claim using the A2.3E evidence schema.
7. Mark conflicting, missing, or unverified claims explicitly; never resolve them by assumption.
8. Run the optional local collector only after independent operator review. It is not executed by this package.
9. Evaluate G1–G12 manually. Every unknown blocking prerequisite fails closed.
10. Select a final outcome only through reviewed evidence and recorded approval.

## Review rules

- Record names and presence states only for environment variables; never values.
- Do not collect credentials, complete URLs, certificates, tokens, customer data, or unnecessary identifiers.
- Prefer text transcription to screenshots. Crop before capture; blur is a secondary safeguard.
- Record provider documentation title, revision date, and public page identifier without copying secrets.
- A support answer must include case ID, date, provider, product scope, and exact non-secret answer.
- Runtime tests require a separately approved isolated environment and test plan.

## Stop conditions

Stop acquisition if a screen, command, file, error, or output may reveal a secret; if environment scope is unclear; if evidence contradicts another authoritative source; or if collection would require network access, database access, configuration change, deployment, or Production traffic.

## Permitted decision outcomes

- `TRANSACTION_POOL_ARCHITECTURE_APPROVED`
- `TRANSACTION_POOL_ARCHITECTURE_BLOCKED`
- `DIRECT_CONNECTION_ARCHITECTURE_APPROVED`
- `SEPARATE_COMMAND_SERVICE_REQUIRED`
- `INSUFFICIENT_EXTERNAL_EVIDENCE`
- `CONFLICTING_PROVIDER_EVIDENCE`

This package never chooses an outcome automatically.
