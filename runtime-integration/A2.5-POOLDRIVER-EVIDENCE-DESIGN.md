# A2.5 Independent Pool and Driver Evidence Contract

## Scope and exclusions

This document freezes the non-executable evidence contract that must be satisfied before any AFEX raw PostgreSQL driver can enter application integration. It authorizes documentation and closed schemas only.

Excluded from this phase are package installation, executable harness code, executable SQL, database or provider contact, credentials, application routes, runtime integration, Production configuration, staging, committing, and pushing.

- Transport decision: `RETAIN_PG_TRANSACTION_POOL_DIRECTION`
- ADR decision: `ADR_REMAINS_VALID_BUT_REQUIRES_AMENDMENT`

## Selected transport decision

The selected future transport is node-postgres `pg` operating through a server-only process-global Pool against the approved Supavisor transaction-pool topology class. This phase is evidence-harness design only. It does not activate the transport.

## Actual current application architecture

Active AFEX application database traffic remains Supabase JS over HTTP/PostgREST, including browser, request-scoped server, administrative, table/view, and RPC access. Application code does not receive a raw PostgreSQL connection and does not own physical checkout, return, reset, or destruction. PostgREST evidence cannot substitute for raw-driver sanitation evidence.

## Frozen runtime and provider topology

- Node.js runtime only.
- Browser use prohibited.
- Next.js Edge runtime prohibited.
- Supabase Edge Functions excluded.
- Raw-driver code must live in a private server-only module.
- Vercel Fluid Compute is the intended future deployment runtime.
- One process-global Pool is permitted per runtime instance after separate authorization.
- Future `attachDatabasePool` use requires package and compatibility approval.
- Supavisor transaction pool is the approved provider topology class.
- Direct PostgreSQL is a local evidence baseline only.
- Session pooling is limited to direct/session contamination evidence.
- No provider endpoint, hostname, URL, port, username, password, or project reference may be retained.

## Security invariants

1. Only a dedicated least-privilege LOGIN may be used.
2. `postgres`, Supabase `service_role`, browser-readable secrets, and public database credentials are prohibited.
3. Verified TLS is required.
4. No raw connection URL, credential, JWT, token, or secret context value may enter logs or retained evidence.
5. The transport exposes fixed domain commands only.
6. Callers cannot supply arbitrary SQL, role names, function names, or identifiers.
7. Tenant, branch, user, authorization, timeout, search path, and row-security context is recomputed inside every transaction.
8. Any identity uncertainty requires client destruction.
9. Secret rotation remains a later provider gate.

## Pool lifecycle contract

One command checks out exactly one client. All command work uses that client. Normal return is allowed only after a successful commit or proven rollback. The application-pool client identity and PostgreSQL backend identity are recorded separately. Local deterministic evidence uses `max=1`; no Production pool size is frozen here.

The Production connection budget must account for:

- provider client limits;
- provider backend limits;
- maximum concurrent Vercel instances;
- pool size per instance;
- reserved administrative capacity.

## Transaction contract

1. Check out one client.
2. Issue explicit `BEGIN`.
3. Establish reviewed transaction-local authority, timeouts, search path, row-security, tenant, branch, user, and authorization context.
4. Execute every statement on the same client.
5. Issue `COMMIT` on success.
6. Issue `ROLLBACK` on failure.
7. Prove terminal transaction state before normal release.
8. Destroy the client whenever terminal state cannot be proven.

Pool-level query helpers are prohibited for command transactions.

## Release and destroy state machine

Frozen states:

- `CHECKED_OUT`
- `TRANSACTION_ACTIVE`
- `COMMITTING`
- `COMMITTED`
- `ROLLING_BACK`
- `ROLLED_BACK`
- `CANCELLING`
- `CANCELLED_ROLLBACK_PROVEN`
- `UNKNOWN`
- `DESTROYED`
- `RELEASED`

Allowed normal-release transitions:

- `COMMITTED` to `RELEASED`;
- `ROLLED_BACK` to `RELEASED`;
- `CANCELLED_ROLLBACK_PROVEN` to `RELEASED` only after every sanitation observation passes.

Required destruction transitions:

- `UNKNOWN` to `DESTROYED`;
- rollback failure to `DESTROYED`;
- cancellation uncertainty to `DESTROYED`;
- socket uncertainty to `DESTROYED`;
- protocol uncertainty to `DESTROYED`;
- identity uncertainty to `DESTROYED`;
- sanitation failure to `DESTROYED`.

Normal release from any other state is invalid.

## Timeout and cancellation contract

The five independent bounded timeout classes are:

1. Database statement timeout.
2. Database lock timeout.
3. Driver/query timeout.
4. Harness process timeout.
5. External request timeout.

Transaction-local database timeouts are established first. Driver and harness deadlines must exceed the intended database timeout by a bounded reviewed margin. Cancellation is attempted at most once. After cancellation, the controller awaits query settlement, attempts rollback, verifies clean transaction state, and releases only if cleanliness is proven. Any unresolved step requires destruction. No timeout may be unbounded.

## Role and context rules

Session `SET ROLE` and `SET SESSION AUTHORIZATION` are prohibited in Production transaction-pool traffic. Only separately reviewed transaction-local authority and context mechanisms are permitted. Session GUCs, temporary objects, cursors, `LISTEN`, and session advisory locks are prohibited. Transaction advisory locks may be used only where separately reviewed. No borrower context may exist after transaction end.

## Prepared-statement prohibition

Named prepared statements are prohibited. A `pg` query configuration must not contain `name`. No provider transaction-pool backend is assumed to preserve prepared state. Borrower-created persistent prepared statements are violations. Provider or PostgREST internal statements are outside this raw-driver contract.

## Local execution tier

The first future live tier is an isolated disposable PostgreSQL 17 environment using the separately approved `pg` driver with a local application Pool configured `max=1`. It proves deterministic checkout, release, destruction, same-backend reuse where applicable, sanitation, cleanup, and post-cleanup absence. It must not depend on the mixed dirty source worktree.

## Provider evidence tier

Provider evidence must prove Supavisor explicit-transaction backend pinning, cancellation and disconnect outcomes, prepared-statement restrictions, client/backend limits, observability, reset behavior, TLS behavior, and rotation behavior. Local success cannot substitute for provider evidence.

## Vercel lifecycle evidence tier

Deployment evidence must prove one process-global Pool per runtime instance, attached-pool idle closure before Fluid suspension, healthy bounded reinitialization after resume or cold start, safe concurrent checkout, and bounded aggregate connections across scaled instances. Local `max=1` evidence must not be reused as the Production setting.

## Production connection-budget gate

Production readiness requires an approved equation whose upper bound is no greater than provider capacity after subtracting reserved administrative connections. Unknown client limits, backend limits, instance count, or lifecycle behavior makes the result inconclusive and blocks activation.

## Package-installation gate

Before package modification, a separately authorized phase must revalidate exact maintained versions, dependency and lockfile impact, Node compatibility, types, advisories, installation behavior, licenses, bundle impact, TLS defaults, parser behavior, and lifecycle compatibility. This contract grants no installation authority.

## SQL-production gate

No executable SQL exists in this phase. Future SQL must be created only under separate authorization, manually reviewed line by line, parser-validated without execution, hash-pinned by the harness, scoped to a disposable non-Production database, and paired with cleanup and post-cleanup attestation.

## A2.5 entry gate

A2.5 application integration remains blocked until:

1. Contract artifacts and hashes pass independent review.
2. Fake-driver lifecycle fixtures pass every state and failure branch.
3. Package and lockfile changes receive separate approval.
4. All applicable local scenarios pass with deterministic retained evidence.
5. Cleanup and post-cleanup absence are proven.
6. Supavisor provider evidence passes.
7. Vercel Fluid lifecycle evidence passes.
8. Production connection budget is approved.
9. Binary and text decoding behavior is frozen and proven.
10. Credentials, TLS, rotation, timeouts, cancellation, release, and destruction contracts are approved.
11. A human reviewer explicitly authorizes application integration.
