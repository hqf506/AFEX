# Pilot Idempotency and Stable Receipt Contract

The idempotency identity is `commandContractVersion + commandType + idempotencyKey + payloadCanonicalHash + authorityBindingCanonicalHash`. The authority-binding hash covers exactly 22 independently supplied fields: command contract/version identity, schema version, local command and idempotency identities, account, tenant, branch, POS employee, managed device, device/enrollment/command generations, key-envelope identity/version, aggregate identity, payload hash, payment attestation, inventory frontier projection and the exact fifteen-field Offline origin-authority v2 reference. No covered field may exist only inside the caller-supplied hash.

Canonicalization is frozen as `afex-authority-binding-canonical-json.v2`: reject unknown, omitted or additional fields; normalize strings to Unicode NFC; recursively order the ASCII field names ascending; emit RFC 8259 JSON with finite numbers and negative zero normalized to zero; encode UTF-8; and hash with SHA-256 lowercase hexadecimal. `aggregateId` and `localAggregateReference` are always emitted, with exactly one represented as explicit JSON `null`. The inactive database writer reconstructs this canonical object from independent parameters, verifies the exact origin correspondence and compares its digest to `p_authority_binding_canonical_hash`; mismatch is `AFEX_OFFLINE_AUTHORITY_BINDING_HASH_MISMATCH`.

`primaryAuthenticatedUserId` describes the immutable origin account, not the current uploader. The exact origin reference additionally binds stable bootstrap ID/generation, enrollment ID, and namespace generation. Replay uses a separately verified current Auth subject/session and POS actor-session reference. The original Auth session may expire without explicit logout; a fresh authorized uploader may submit only after active same-account bootstrap validation in the same tenant/branch/device scope. Explicit logout makes retained work inaccessible until same-account Online recovery raises the stable bootstrap generation. The inactive database writer rejects cross-account or cross-scope substitution and never treats UUID equality or `service_role` transport as authentication.

An identical submission returns the same immutable `StableServerReceipt v1`. A repeated key with a different payload hash returns `IDEMPOTENCY_PAYLOAD_CONFLICT`; a different immutable authority binding returns `IDEMPOTENCY_AUTHORITY_BINDING_CONFLICT`; any explicit scope mismatch returns its corresponding account, tenant, branch, employee, device, generation, command or contract-version conflict.

Receipt replay is authority-last, not receipt-first: fresh trusted validation of account, active bootstrap, tenant, branch, employee enrollment, managed device, revocation state, namespace, all generations, and device key-envelope binding must succeed before a stored receipt may be returned. The PIN never participates in receipt or encryption authority. Shadow commands are blocked by the exact `order.create` database allowlist before any receipt response.

The receipt contains the contract version, server command identity, idempotency key, payload hash, authority-binding hash, terminal disposition, deterministic result code, completion time and response reference. It never contains payment credentials or key material.

No transport response marks a command synced without a validated stable receipt. Aborted, timeout, unknown and HTTP-success-without-receipt outcomes retain the command for safe retry.
